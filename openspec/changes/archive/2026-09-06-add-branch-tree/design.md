## Context

现状（读代码确认，非推测）：

- **数据已经在手**：`runs:list` 返回的 `RunSummary[]` 每条都带 `id` / `parent` / `status` / `steps` / `tokensIn` / `tokensOut` / `durationMs`（`apps/desktop/src/shared/ipc.ts:27`）。parent 关系足以建树，无需新通道、无需读文件
- **缺的只有 fork 元数据**：`RunSummarySchema` 现在没有 `fork` 字段，所以界面只能在列表里显示一个「分支」文字标签，画不出「从哪个 span 分出来、改了什么」。而 `meta.fork` 在 main 侧 derive 时就在手（`deriveRunSummary` 的入参是完整 `RunRecord`），透传成本为零
- **口径陷阱（必须写死）**：`deriveRunSummary` 是对 `readRun` 的原始记录现算的，所以列表里的 `steps` / `tokens` 是**本 run 自身新增 span** 的聚合，**不含祖先前缀**；而 `getRun` 返回的是 `resolveBranch` 拼接后的完整轨迹。这两个口径目前在不同面板各说各话，分支树第一次把它们摆在一起，必须显式区分，否则用户会把「分支增量 3k」误读成「全程 3k」
- **既有可视化先例**：预算地图用 ECharts（`BudgetMap.tsx` 懒加载）、详情页用 Monaco。分支树是第三种可视化形态，但它是**关系图**而非图表

## Goals / Non-Goals

**Goals:**

- 把 run 之间的 parent / fork 关系画成一张确定性的、可单测的图
- 让 2–4 条分支的代价与结局能并排看，并给出共同祖先与增量差
- 全程只读派生：不加写通道、不改 trace 格式、不加依赖

**Non-Goals（设计层的额外边界）:**

- 不做树的折叠 / 展开子树（分支数量在千级以内，一屏放得下；需要时再补）
- 不对节点做虚拟滚动
- 不把「视图模式」持久化
- 不复用 `resolveBranch` 做树构建（它是「拼接一条完整时间线」的语义，树要的是「关系拓扑」，两者输入相同但目的不同；混用会让树依赖祖先文件的可解析性）

## Decisions

### D1：树在渲染层从既有 `runs: RunSummary[]` 派生，不新增 IPC 通道

- **选**：渲染层派生（`buildRunForest` / `layoutRunTree` 放 `src/shared/derive.ts`）
- **备选（否决）**：main 侧建好树结构随 `runs:list` 一起返回。否决理由——树只是既有数据的一次投影；放进 IPC 就多出一份「可能过期」的派生结构，违背本项目「数据派生不累积、不缓存」的不变量（`derive.ts` 文件头纪律）。且渲染层派生后可直接用 vitest 断言布局，不需要起进程

### D2：`RunSummary` 增 `fork: { at_span, edit_field } | null`，不带 value

- **选**：只透传分叉点 span id 与被编辑字段名
- **备选（否决）**：整个 `ForkSchema`（含 `edit.value`）透传。否决理由——`edit.value` 可能是整段 tool_result 或完整 messages 数组（KB 级 × N 条 run），而 `runs:list` 是冷启动时的一次性全量传输；树只需要字段名做边标签。要看具体内容时进详情，既有 DetailPanel 已呈现编辑值
- 兼容性：新字段对老 fixture 与老载荷无要求（zod 侧随主 spec 加，老数据按「无分叉摘要」处理）

### D3：手写确定性布局 + 手写 SVG，不用 ECharts tree

- **选**：`layoutRunTree` 手写「叶子计数法」——先自底向上算子树占多少纵向槽位，再自顶向下分配 y；`x = depth × (节点宽 + 层间距)`。渲染用 SVG（DOM，可直接挂 Tailwind class、`title` 提示、键盘聚焦）
- **备选（否决）**：ECharts `series.type="tree"`（已在依赖里，零新增依赖看似更省）。否决理由——① ECharts 的布局为美观做了自动正交/径向排布，坐标不可控，无法单测「确定性 / 不重叠」这两条硬要求；② 它是 Canvas 渲染，节点内多行中文 + 勾选交互要靠 formatter 拼字符串，越做越绕；③ 为此把 300KB 图表运行时拖进「打开应用先看的那张图」的冷启动路径不划算
- 代价：连线样式要自己画（用三次贝塞尔，父子间水平入/出的经典曲线），约十行代码

### D4：横向树（根在左，分支向右生长）

- **选**：横向，节点卡片固定宽（约 200px），内含三行：任务名 / 时间 · 状态 / 增量数字
- **备选（否决）**：纵向（根在上）。否决理由——task 是中文长文本，纵向树每个节点的可用宽度被兄弟数量切分，中文会挤成竖排或大片截断；且调试台信息流天然左→右（列表 → 树 → 详情），横向与之一致

### D5：孤儿与成环一律「提为根 + 显式标注」，不隐藏、不报错

- traces 目录是用户能手工摆弄的文件夹：可能删掉中间某个 run、可能只拷进来半个家谱。隐藏 = 用户找不到自己的数据；报错 = 一个坏关系毁掉整张图。与既有 `RunRepository`「单文件读取失败隔离成列」同一哲学
- 实现要点：按 id 建 Map → **迭代式**（非递归，避免深链爆栈）沿 parent 行走，行走路径用 Set 记录；遇到「已在当前路径中」的 id 即判定成环，把该 run 提为根；父 id 不在 Map 中即判定父缺失，同样提为根
- 单测用内存数组构造（不往数据目录写环数据），冒烟脚本只造正常家庭

### D6：对照面板只用内存里的 `RunSummary`，不再读文件

- 对照要的指标（状态 / 步数 / 工具数与出错数 / tokens / 耗时 / 分叉点摘要）`RunSummary` 全有，无需 `getRun`
- **共同祖先** = 两条祖先链的最后一个公共 id（把链转成数组，从尾往前找第一个同时存在于另一条链的 id）。其中一条是另一条的祖先时，结果就是那条祖先 run，UI 单独标注「A 是 B 的祖先」
- **全链累计** = `deriveChainTotals` 沿 parent 链把各代增量求和；遇父缺失返回不可得（UI 呈现「—」），**不补 0、不估算**。增量差 = 两条 run 的全链累计相减，两者任一不可得时该差值同样不可得
- **无共同祖先**（两条 run 分属不同根、且两条链都完整）时 SHALL NOT 计算增量差——没有可比基线，硬凑一个差值会让用户以为两条 run 有共同起点。此时只呈现各自指标与累计增量，共同祖先位置标注「无（分属不同根）」
- **判定不完整**（任一条链上出现父缺失）SHALL 与「无共同祖先」分开呈现为「判定不完整（存在父缺失）」，并且同样不计算增量差（此时累计增量本身也不可得）。**不能合并成一种文案**——用户删掉中间某个 run 后，两条其实同源的分支会被误报成「本来就不同源」，这属于用错误结论代替「我不知道」

### D6.1：累计增量的措辞不许含「总」字

沿链求和在物理上不是「从头连续跑一次」的消耗：各代 `durationMs` 是各自墙钟跨度之和（中间夹着用户看结果、改内容、点重跑的空档），而子 run 首次 `llm.call` 的 `usage.in` 又含父前缀（replay 派生的 messages），所以累计值系统性高于「一次性跑完」的真实消耗。因此 UI 一律写「累计增量（沿链求和）」，禁用「总耗时 / 总成本 / 总消耗」。诚实原则与项目既有做法（`ttft_ms` 非流式记 0 而非拿总耗时冒充）同源。

### D7：视图模式是渲染层 `view` 状态，不进 IPC、不进 settings、不持久化

- 纯 UI 偏好。持久化要引入磁盘写（settings 是既有写路径，但为一次视图切换占用它不值当），留给后续独立小改动

### D8：状态色沿用既有语义

- `completed` 绿（emerald）、`crashed` 琥珀（amber，标注「运行中断」）、有工具出错时红色标记——与 `RunList.StatusBadge`、`SpanTree` 的 errored 配色保持一致，不发明新配色

### D9：冒烟数据用 `JsonlTracer` 直接写，不跑真模型

- fork 在真实路径上需要 API 调用才会产生，但树视图只看 `meta.parent` / `meta.fork` / 自身 span。用 `JsonlTracer` 手写 meta + span 即可造出**结构合法**的家庭：1 根 + 2 兄弟分支 + 1 孙分支 + 1 代理链（`source.kind="proxy"`、`fork.edit.field="messages"`）
- 诚实边界：这批数据是结构合法但非引擎运行产物，文件名统一前缀 `tree_`，脚本文件头写明用途，避免与真实 run 混淆，也避免有人拿它去试「在此重跑」（其 config_hash 不真实，会被 replay 校验拒绝——这是既有行为，不因此放宽）

## Risks / Trade-offs

- **[渲染层建树的性能]** → 布局 O(n)、渲染 O(n)。一个 run 至少对应一次真实 API 调用，正常用户攒不到几千条；暂不做虚拟化与折叠，实测卡了再补。真出现超大目录时，退路是先按 root 分组折叠成多棵树
- **[SVG 大画布的浏览体验]** → 三档缩放（75 / 100 / 150%）+ 滚动容器，不做自由拖拽平移。若用户反馈「找不到自己在哪」，再补「回到选中节点」按钮
- **[增量 / 全链口径混淆]** → UI 两行分开且各带口径名（「本 run 增量」「全链累计」），`deriveChainTotals` 由单测守护（含父缺失返回不可得）
- **[手写布局与 ECharts 视觉语言不一致]** → 两者不同屏出现（树是全宽视图，预算地图在 DetailPanel 内），无并排对比压力
- **[老 run 无 fork 字段]** → zod 侧该字段可空，老 fixture 与老 trace 无需改动，不产生破坏性变更
- **[分支树暴露了「列表数字是增量」这个既有不一致性]** → 本变更不修改既有列表的口径（改了会影响既有测试与用户已形成的认知），只在树与对照面板显式标注；是否统一列表口径属独立议题

## Migration Plan

无数据迁移：`trace` 格式不动、既有 run 文件不动、既有 IPC 消费者不受影响（新增字段为可选方向）。

回滚：删除新增组件与 `store` 里新增的 `view` / `compareIds` 字段即回到原状；`RunSummary` 的 `fork` 字段即使留在 schema 里也不影响任何既有行为。
