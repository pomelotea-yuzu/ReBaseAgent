# 桌面渲染层模块拆分设计

## Context

基线与范围见 [proposal](proposal.md)。三个目标文件存在以下可直接核实的职责边界：

| 当前文件 | 已有职责 | 主要风险 |
|---|---|---|
| `components/DetailPanel.tsx`（2161 行） | 详情入口、prompt 编辑、result 分叉编辑、LLM/tool/step 展示、缓存与草稿提示 | 搬迁时改变组件类型或 key，导致草稿、Monaco、核对状态重建；漏迁确认入口 |
| `components/WorkspaceFileView.tsx`（1866 行） | `WorkspaceFileView` 读取连接、`WorkspaceFileViewBody` 布局、`FileContent` 查看器 | 两侧读取被合并、旧响应串入新目标、Monaco 监听未释放、尺寸与滚动恢复退化 |
| `store.ts`（3769 行） | `AppState`、初始化、全部 action、提交/核对/结果收尾、导航恢复、轮询/订阅/等待者/派生缓存 | 多实例、循环依赖、spread 覆盖字段、原子更新被拆开、资源重复注册、selector 返回新引用 |

`AppState` 当前约占 880 行，简单挪到一个 types 文件仍会集中职责；应随功能边界分成接口，再聚合为完整类型。现有 `lib/` 已有草稿、提交、比较、轮询等纯判据，本轮只整理连接和承载，不另建同类规则。

`store.ts` 已导出 `MAX_COMPARE`、`ExperimentSourceState`、`idleExperimentSource`、`stopOperationStatusPolling`、`useAppStore`。`DetailPanel.tsx` 和 `WorkspaceFileView.tsx` 也有测试或其他组件直接消费的导出。实施前枚举全部导出和导入方，不能只核对默认页面入口。

## Goals / Non-Goals

目标是让一次功能修改有明确模块归属，同时保持当前全部可观察行为、状态形状和入口兼容。具体排除项见 proposal。所有任务尚未实施，不把本文树形布局当成已落地结构。

## Decisions

### D1：按职责建模块，保留稳定入口

建议结构如下；可在实施前核对依赖后细调文件名，变更职责、状态归属或生命周期须先修订设计和任务。

```text
renderer/src/
  components/
    DetailPanel.tsx                 # 详情选择和组合；兼容原公开导出
    detail/
      PromptForkEditor.tsx          # prompt 草稿、核对和提交接线
      ResultForkEditor.tsx          # 原 ForkEditor；普通/隔离 result 接线
      LlmCallDetail.tsx             # LLM 调用容器及展示
      ToolInvokeDetail.tsx          # 工具调用容器及展示
      StepDetailView.tsx            # step 展示
      DetailShared.tsx              # 小型公共展示、缓存提示、草稿列表与来源提示
    WorkspaceFileView.tsx           # 读取连接；兼容原公开导出
    workspace-file/
      WorkspaceFileViewBody.tsx     # 目录、检查点、工具条与导出面板布局
      FileContent.tsx              # 两侧/单侧查看、差异与编辑器生命周期
      types.ts                    # 原跨上述层的 props/selection 类型
  store.ts                        # 单次 create、分片组合和兼容导出
  store/
    types.ts                      # AppState 聚合及带类型的上下文
    runtime.ts                    # 资源组合入口；不成为第二份业务状态
    runtime/                      # 轮询、代理订阅/等待者、按引用派生缓存
    slices/
      runs.ts                     # 列表、详情、来源筛选和选择
      reading.ts                  # 调用/文件阅读状态与定位
      drafts.ts                   # 草稿、提交关联和执行确认
      operations.ts               # 握手、统一提交、核对和执行入口适配
      results.ts                  # 结果核实、草稿收尾、通知和导航意图
      compare.ts                  # 比较读取、pair、侧目标与返回
      navigation.ts               # 创建/辅助工作区入口和返回、树视图
      configuration.ts            # 设置、代理状态/变化协调和录制草稿应用
```

分片类型放各职责模块或相邻 `*.types.ts`，聚合文件只负责交叉类型组合。`DetailShared`、`runtime` 或某个分片若再混入多个独立职责，应继续按实际边界细分，不能把原大文件改名挪走。业务相近且只使用一次的少量 helper 留在所属模块，不追求每个函数一个文件。

原入口兼容导出必须指向同一个实现，禁止留旧实现再复制新实现。新内部组件不得回引原容器来取 helper；共用展示与类型下沉，避免兼容 re-export 构成循环。Monaco 继续通过既有懒加载包装消费，纯类型导入不得变成运行时 Monaco 导入。

规模目标为 `store.ts` 和两处 UI 入口成为数百行以内的组合/连接层，内部模块通常在约 300–800 行内；这些是审阅提示，不是硬性 lint 门槛。验收须列拆分前后物理行数、职责和超出提示范围的理由；不能删注释、压行或把逻辑搬到无职责名称的 utils 文件来满足数字。

### D2：单个 store、显式上下文与唯一字段归属

仅 `store.ts` 调用一次 `create<AppState>`，其路径优先解析现有文件；内部引用一律显式指向具体模块，避免 `store.ts` 与 `store/` 目录入口歧义。分片以完整 store 的 `set/get` 及有限 runtime 能力为上下文，不调用第二次 `create`，不导入 `useAppStore`，也不通过模块顶层缓存 store 实例。跨分片调用使用执行时 `get()` 的 action 或显式注入的单一协调函数；分片之间无运行时互相导入。

初始化阶段只创建初值、action 闭包和未启动的资源对象；不得在 zustand state 尚未就绪时调用 `get()` 或读取其他分片。runtime 依赖使用惰性回调，启动时点沿用现有 action/组件调用，不因模块加载立即开始订阅、轮询或 IPC。

字段及 action 各有唯一所有者；建立全量归属表，记录跨领域写入的协调函数。类型检查加组合键集合检查验证无缺失、无重复覆盖。跨领域业务更新仍允许在原协调函数中用一个 `set(state => patch)` 一次提交，不能为了分片形式依次调用几个 setter，暴露原本不存在的中间状态。原有动作顺序和 `await` 边界保持。

### D3：runtime 管资源，纯判据与业务状态继续各归原位

轮询 state/timer、代理变化解绑句柄、状态读取静默等待者、`createReturnFactsOf` 按输入引用的缓存分别由单一 runtime 所有者持有。按 store 实例组合一次，兼容旧的停止轮询导出；业务事实仍在同一个 store，已有 `lib/operation-polling.ts` 等继续提供判据。

保持 ensure/release 的幂等性和现有停止语义，不因为拆分重新设计取消：停止轮询清计时器且保留在飞响应守卫；proxy 在尾随读取全部结算后才唤醒等待者；订阅释放与重新建立不重复处理同一通知。资源工厂本身不得在导入时启动资源，也不得为每个分片或组件各建一份计时器/订阅。

selector 继续返回稳定 action 和缓存引用；特别保留 `createReturnFactsOf` 在 `createReturnLocation` 与 `runs` 引用未变时的返回对象身份。禁止 getter 每次临时拼装新对象触发 zustand v5 的无限重渲染。对资源测试显式停止/解绑并使用现有测试复位方式；本轮不另建生产用热更新框架。

### D4：迁移动作不能改变异步与授权纪律

统一提交只有一份：握手 → 门禁 → 绑定 operation 身份 → 发送 → 核验回执 → 状态核对 → 核实结果/收尾。执行入口不得绕过它。比较、详情、文件与结果读取各自保留原有完整身份、generation/attempt 和版本判据；旧 epoch 响应、旧代理事实不能恢复新会话的许可或覆盖选择。

草稿正文、revision、冻结、提交快照、closure、导航意图继续各依现有数据结构运作；只有可信自有正常结果才能清理匹配修订，旧结果不得清新草稿。设置往返、配置变化、来源失效与退出协商的许可失效和关闭保护保持。未知状态只核对，不自动重发；拆分不引入请求重试或额外模型调用。

### D5：UI 搬迁保持挂载身份、布局与文件语义

组件定义置于模块顶层，原有 key、条件渲染和编辑器 model 身份保持。拆分是源码组织变更，执行中的页面不能由于新增包装层改 DOM 布局、焦点范围、CSS 高度链或 ref 的目标。对于现有就会卸载的切页，继续由既有会话草稿/阅读恢复承接，不承诺永不卸载。

文件两侧状态、原始内容和缺失/失败含义不能被共享 loading/error 合并。Monaco 继续只读，原文查找/复制、模式适配、取消监听、滚动和视图恢复保持；特别保留按实际文字区选择 diff 模式及 `useInlineViewWhenSpaceIsLimited: false` 的既有行为。目录和内容区不增加破坏 `min-height`、flex/overflow 链的 DOM 包装。

导出资格、确认和反馈仍来自所选 run+检查点；切换后迟到反馈不串目标，离开再返回沿用现有状态规则。读取、重试和展开操作不变成执行或导出。

### D6：测试随保证迁移，不能只扩大源码搜索范围

评审基线 `ddcfd2a` 上直接通过 `readFileSync` 或封装的 `read/R/rendererSrc` 读取三个目标的测试共 **36 个文件**，已逐项列入 [静态测试迁移基线](test-migration-baseline.md)。实施从这份完整文件清单复核，不从原先的举例增量补漏；实施起点若有新增/减少，记录差集与原因，36 是当前快照，不是测试数量上限。任务 1.3 仍须逐个展开到测试名和断言，不能把这张文件级清单当成迁移已完成。

同时单独枚举动态导入原入口的测试与生产消费方。静态读源码断言迁移到实际承载模块或由真实 DOM/action 保证；动态导入继续从原入口消费实际组合后的 `useAppStore` 和组件，验证兼容导出与实例身份。一个文件同时具有两类检查时分别建账，不因静态路径修改而漏掉动态行为。保持行为测试使用可控 Promise/假时钟验证请求数、状态序列和迟到响应，不能只测单独分片的理想输入。

每项记录「旧测试名/断言与文件位置 → 原保证 → 新承载与生产消费者 → 验证方式及新断言位置」。特别点名 `run-list-nav.test.ts:238–250` 的固定文件清单、`budget-reachability.test.ts:325–338` 的 Monaco 清单及包装接线、`draft-compare-grid.test.tsx` 等跨文件计数。原路径搬迁后必须追到实际生产实现，不能让否定断言只在已经搬空的入口上通过；清单增删逐项写理由。

原本针对单文件的静态接线检查改查明确的生产导入路径和实际消费者；禁止把整个源码目录拼接后搜字符串，或删除断言、改 `.skip`、只计新导出数量。能由 action 或真实 DOM 验证的保证优先由其承接；确需静态检查的单例创建、依赖方向和懒加载边界使用导入图/语法结构检查，不以注释命中证明接线。使用现有 TypeScript/vitest 能力，不新增架构测试依赖。

实施基线需记录测试名、实际执行/跳过数、已知失败与构建状态。测试可按职责移动，数量可因合理参数化变化，但每项旧保证须有去向，新增跳过或删除须解释且不得削弱等价要求。历史截图和测试通过记录只提供参考，本轮须在最终源码上重新验证。

## 实施顺序与验收范围

1. 固定源码/测试/运行路径基线和字段、导出、资源、断言迁移表。
2. 拆详情展示，再拆两个编辑器；确认导出和恢复后进入下一阶段。
3. 拆文件布局与内容查看器，验证两侧读取、生命周期和导出。
4. 拆 store 类型和资源接口，再按纯阅读 → 草稿/导航/比较 → 操作/结果/配置顺序迁移；唯一协调逻辑整体搬迁，禁止新旧两套并行。
5. 用最终组合 store 跑竞态与资源断言，运行全仓门禁与 desktop build，再做真实 Electron 验收。

每个任务不超过 2h，超出按状态域或场景继续拆；全量验收按套件拆任务。所有实际运行日志和证据在 [索引](evidence-index.md) 回填。Electron 使用独立受控数据目录与现有本地 mock 服务，禁止改用户数据或为截图直接改 store/伪造 operation。正常状态通过界面生成；坏附件/缺来源等异常可在独立 fixture 上受控注入并登记。

## Risks / Trade-offs

- 分片互调容易形成循环：通过类型层、显式上下文和唯一协调者控制；依赖图检查须覆盖入口 re-export，不能只靠构建碰巧通过。
- 资源按实例包装可能改变初始化/停止顺序：先固定订阅数、轮询数、等待队列与缓存引用的行为基线，再搬迁，不能顺带改协议。
- 测试位置契约数量多：保留逐项迁移表并分阶段回归，不靠最后一次全绿倒推覆盖完整。
- 纯拆分带来的文件数会增加：只在真实职责边界拆，接受仍有中型组件；不声称包体积、渲染性能或产品可用性必然改善。

## 归档与后续发行

归档前核对本 delta 19 个场景的证据、旧断言去向和依赖/规模报告。保存合入前完整主 spec 的 requirement 标题与「所属 requirement + scenario 标题」集合，delta 合入后逐项求差，既有集合缺失必须为零，新增集合须与本 delta 一致；只比较总数不能证明无丢失。当前基线为 95 条 requirement，实施或归档起点若变化，以记录的新基线集合为准并解释差异。同步架构说明和当前状态。本轮不安排新 portable 包；后续发布仍须独立固定候选并执行实包验收，开发版 Electron 证据不能替代发行物验收。
