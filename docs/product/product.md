# ReBaseAgent 产品方向定稿（Product Direction）

> 定稿日期：2026-09-05 · 状态：**真产品方向**（非纯作品集/自用工具）
> 来源：产品策略探讨闭环（定位 → 接入 → 时间旅行边界 → 触发场景 → V3 终态 → 普及性）
> 范围：本文件为产品方向定稿，工程实现见 `openspec/specs/*` 与 `HANDOFF.md`

---

## 1. 一句话定位

**ReBaseAgent 是本地优先的 Agent 调试、实验与测试平台**：让写 Agent 的开发者像调试普通程序一样，去「看 span、改某步、重跑、分支对照、回归测试」。

内核比喻：**上下文即程序（context is the program）**。Agent 跑歪时 bug 不在 loop 代码里，而在某一步的上下文里（脏 tool_result / 偏 prompt）。ReBaseAgent 把传统调试器的能力（看变量、改一行、重跑、分支对照）搬进 Agent 世界。

---

## 2. 目标用户与 JTBD

- **核心用户**：独立开发者 / 小团队，正在用 LLM API 写 Agent（RAG、coding agent、工作流自动化）。
- **痛点排序**：① 重跑成本高（每次从头烧 ¥）→ ② 隐私敏感（不愿 trace 上 LangSmith 云）→ ③ 行为不稳需复现/回归。
- **主动放弃**：纯 ChatGPT 网页用户（无开发需求）；超大厂（已有内部 observability 栈）。

### 四条触发场景（JTBD — 用户何时双击打开它）

| # | 状况（用户此刻在做什么） | ReBaseAgent 做什么 |
|---|---|---|
| 1 | Agent 跑歪，不知哪步把模型带偏 | 打开 span 时间线，点每步看模型当时看到的完整上下文 |
| 2 | 某步 tool_result 脏了，想改了看模型能否挽回 | 改那步 tool_result，从那步重放，只花后半段 API 费（前缀缓存命中） |
| 3 | 想换 prompt / 模型，对比同一段对话新旧谁更好 | 从 step 0 开分支换 prompt，同前缀缓存命中做 A/B |
| 4 | 偶发 bug 只出现过一次，要复现/甩给同事 | 导出 trace，精确指到跑歪的那步（未来进 CI 当回归测试） |

- **边界（同样重要）**：一次 `chat.completions` 调用就完事、或纯确定性脚本（bug 在代码不在上下文），用不着它。
- **他们现在的替代**：`print` + 日志（看不到模型当时完整输入、不能改一步重跑）/ LangSmith（能看不能改并重跑、数据上云）。ReBaseAgent 卡的就是这两条缝：**能改 + 本地**。

---

## 3. 护城河

- **时间旅行**：能改某步并从那步重跑（LangSmith 只能看）。
- **本地优先**：数据不出机器（隐私敏感团队的卖点）。
- **真正壁垒（需抢先占住）**：分支树数据结构 + 前缀缓存命中保证 + DX + 先发开源心智。incumbent 补「重跑」容易，抄「分支树 + 本地优先 + 时间旅行」难，但时间窗口有限。

---

## 4. 零摩擦接入（活下来关键）

- **推荐落地 = 本地 LLM 录制代理**：用户在自己的 Agent 应用里**只改一行** `base_url` 指向 ReBaseAgent 起的本地代理（如 `http://localhost:<port>/v1`），自己的 key **一字不动**。代理透明转发请求到真实 provider，同时把每次调用录成 span。
- **key 处理原则**：录制 / 看时间线 / 改某步 tool_result = 纯本地数据操作，**不需要 key**；仅 **fork 重跑** 需 key，那时复用代理收到的 key（内存/本地加密暂存），或把改好的续跑上下文导回用户应用重跑——**key 始终不进 ReBaseAgent 存储**。
- **兜底**：当前 SettingsDialog 手工填 key 仅为最后手段（产品化须消除——避免「key 只能复制一次、要删了两边填」的死结）。
- **与时间旅行的断层（2026-09-05 评审定稿，方案 a）**：Spec #4 的 fork 语义依赖 `tool.invoke` 叶子 span / 工具表 / config_hash，而代理只看到一串独立 `chat.completions` 请求——代理录的 run 天然不可走既有 fork 路径。**定稿方案 a：代理侧做「单请求级最小分叉」**——从代理 run 的 llm.call 详情编辑 messages 中任意一条 → 经代理用暂存 key 重发 → 记为 fork run。它让 JTBD ②（改脏上下文重发）在代理路径上也成立，且钩子 demo 走这条路拍。既有 replay 包路径（SDK 接入）不受影响、语义不变。
- **信噪比防线**：代理会录下用户全部 LLM 流量（含试探/聊天），须有 `meta.source` 标记、run 列表过滤、可暂停录制，否则「零摩擦」变「零信噪比」。
- **辅助**：开放 trace 格式 + 一行 SDK `@rebaseagent/trace-sdk`；支持从 LangSmith 导出、从框架（LangChain/AutoGen/CrewAI）转换导入。

## 5. 时间旅行的边界（关键架构决策）

- **默认 world-free 重放**：replay **不复执行任何工具**，直接把录下的 `tool_result` 喂回模型重新推导。外部状态（文件 / DB / API）不参与，trace 内自洽。这**消解了「回到某步但文件已变」的不一致**——重放时模型看到的是当时记录下来的旧上下文，磁盘上的新文件根本不被读取/写入。
- **仅当用户显式「真重跑带副作用的工具」时**（如「把这次写文件真重写一遍」），才在**分支隔离世界**里执行：
  - 方案 A · COW overlay（写时复制层）：每个分支挂一层 overlay 文件系统，工具写入只落在该层；回到某分支 = 切回那层 overlay，其他分支与真实文件都不动。
  - 方案 B · 逐步快照：每个带副作用的工具执行前对受影响文件打快照（git 式）；replay 到 step N 时先 restore 再执行。
  - 触发由 `sideEffect` 标志驱动：`false`（只读/确定性）可安全复跑或 replay 录制结果；`true`（写文件/发请求/改 DB）重跑须进隔离世界。
- **与现有不变量对齐**：OpenAI function calling 子集为工具协议；`sideEffect` 默认 true 为 replay 分级预埋（本决策让它「长出牙齿」）。

## 6. 产品化缺口（优先级高于堆功能）

MVP 证明了技术可行，但工具类产品最常见的死法是「功能很全、没人装」。活下来靠**活下来三件套**（近期，优先级高于 v2 功能深度）：

1. **零摩擦代理 + 一键导入**（让接入成立）
2. **钩子 demo**（30 秒 aha 视频 + 可交互教程 trace）：优先演绎 JTBD ②——改第 N 步脏 tool_result → 只重跑后半段（成本约 1/4）
3. **打包分发**（portable exe / NSIS 安装包，别让用户 `pnpm dev`）
4. **协作分享**（导出 trace 给同事看跑歪点）

## 7. 路线图（按产品价值排，非技术顺序）

- **MVP（已完成）**：#1 trace-sdk → #2 agent-loop → #3 调试台 UI → #4 时间旅行切片（replay）→ #5 预算地图 + Monaco（全部 archived）
- **活下来阶段**：零摩擦代理 + 导入 + 钩子 demo + 打包分发
- **v2**：完整时间旅行（分支树 UI、改 prompt、多分支对照）
- **v2+**：分支实验 A/B（同前缀换模型 / prompt 做低成本对比）
- **v3**：Trace-as-Test 进 CI（一次运行当回归测试资产）

> 关键判断：**第一步是「让人装得上、导入就能玩」，不是继续堆 v2 功能深度**。没人装，分支树再漂亮也没观众。

## 8. V3 成品形态

本地优先桌面应用（portable exe），四层能力递进：

```
零摩擦录制 (MVP+)  →  时间旅行调试 (v2)  →  分支实验 A/B (v2+)  →  Trace-as-Test (v3)
```

- **交付物**：portable exe / NSIS 安装包的本地桌面应用，双击即用，数据全在本地、不出机器。
- **商业形态**：代码 MIT 开源、本地免费；团队版卖「共享 trace 库 + 多人标注 + 自托管」，不碰数据主权（不做 SaaS 云锁数据）。
- **用户心智**：写 Agent 时的「DevTools + 单测框架」二合一。
- **明确不是什么**：**不是 agent 构建器**（不会让你在 UI 里拖拽搭 Agent）。用户始终是「已在自己代码里写 Agent 的人」，ReBaseAgent 只负责录下来、调明白、试稳。这条边界是护城河成立的前提。

---

## 9. 商业模式

- MIT 开源 + 本地免费。
- Pro / 团队版：共享 trace 库、CI 集成 Trace-as-Test、多人标注。
- **红线**：勿为变现破坏「本地不出机器」卖点（慎做 SaaS 云——会和核心卖点打架）。

---

## 10. 普及性判断

- **现实天花板**：写 Agent 的开发者 niche 内的**品类标准**（非大众消费品，类比 Postman 在 API 开发者中的地位）。
- **利好**：Agent 开发者群体爆发式增长；痛点真实（LangSmith 只能看不能改重跑）；开源 + 免费 + portable 口碑易扩散。
- **阻力**：调试器 TAM 天生窄；incumbent（LangSmith / Langfuse）可能补 rerun；本地优先削弱网络效应（无云分享飞轮，协作靠导出/自托管）。
- **关键一跃**：v3 进 CI（团队接入即粘住，从个人玩具变团队基础设施）+ 抢在 incumbent 补齐前占住开源心智。

---

## 11. 平台化（已否）

- **仅可行性探讨，不纳入开发计划**。维持原 v2/v3 技术路线。
- 探讨结论备查：agent-loop（运行时）+ trace-sdk（录制）+ replay（重放）已是「平台运行时三件套」；若未来做平台，缺的只是「让用户创建 Agent」那层（Agent 工作室 / 工具系统 / 导出分享）。当前不做。
