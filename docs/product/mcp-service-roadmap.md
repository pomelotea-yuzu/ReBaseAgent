# MCP 服务演进规划

更新：2026-10-26。状态：**MCP0（接口与接入准备）与 MCP1（只读诊断首版）已实施并归档**（change `add-readonly-mcp-diagnostics`，2026-10-24）：七只读工具 + 真实 stdio 全量协议 + 零写入/零执行复核 + WorkBuddy 5.9.0 真实客户端两轮验收 + 接入指南；**MCP1 已随 `v0.6.0-rc.1` 发行，MCP2 已随 `v0.7.0-rc.1` 发行（十三工具）**。接入方法见[只读诊断接入指南](../guide/mcp-readonly-diagnostics.md)。MCP3 仍为规划，能力排序以正式路线为准。本文细化[正式产品路线](evolution-roadmap.md) §3.3；能力排序以正式路线为准，具体接口与执行契约通过后续 OpenSpec 提案设计和验收。

## 1. 目标与范围

让开发者在已有的 AI 开发工具中调用 ReBaseAgent 的调试能力，完成“找到失败运行 → 读取相关步骤 → 比较修复分支 → 核对测试证据”。桌面工作区继续提供人工阅读、编辑和结果复核入口；两种入口使用同一份事实和校验逻辑。

本体系把 **ReBaseAgent 作为 MCP 服务器**，由支持 MCP 的应用作为客户端连接。让内置 Agent 调用外部 MCP 工具是另一项需求，涉及新的工具和状态适配，按 I／R5 单独评估，不属于本体系。

MCP 只提供访问入口，不增加历史状态恢复能力。连接成功不代表已有项目接入 I 通过，也不代表任意第三方 Agent 的文件、数据库或远程服务能被恢复。

## 2. 编号与排期

采用 `MCP0–MCP3`，与开源传播的 `M0–M4` 区分。以下均为计划，编号不代表版本号或发布日期。

| 阶段 | 用户得到的能力／交付物 | 安排与进入条件 |
|---|---|---|
| MCP0：接口与接入准备 | 一个明确客户端的接入方案、共享只读查询边界、返回结构和数据范围 | R2.2 设计期间可准备；实际接口提取单独提案，不扩大当前渲染层重构范围 |
| MCP1：只读诊断首版 | 查询运行、步骤、错误、运行比较与检查点文件 | R2.2 首版验收后安排，可在 R3 期间独立推进；复用届时已验收的文件比较能力 |
| MCP2：测试证据查询 | 查询真实命令、日志、退出码、执行环境和产物来源 | R3 首个受支持环境验收后，消费实际记录；不以材料包导出完成为前提 |
| MCP3：受控执行入口 | 按需发起已支持的实验、重跑或测试，并查询实际结果 | R3 首版后由真实使用需求驱动，执行授权与操作状态契约另行验收；参数修改后重做还依赖 R4 |

R2.2 与 R3 继续保持核心交付优先级。MCP1 不成为二者的前置条件；若共享查询层提取或客户端接入工作明显扩大，顺延到 R3 首版后。MCP1／MCP2 无需等待完整 R2.3、R4 或 R5。MCP3 消费已交付能力，不自动扩展执行范围。

当前渲染层模块拆分主要整理组件和 store，不是 MCP 的技术前置条件，也不承担 MCP0 的主进程或共享接口改动。

## 3. MCP0：接口与接入准备

先选一个明确客户端及版本，验证其本地连接、配置和错误呈现方式。优先评估独立 Node 进程与本地 stdio，便于复用包层代码并保持桌面便携能力；最终运行形态、启动命令、运行时分发及更新方式在实施设计中确定。首版不预设常驻网络服务、远程共享或多租户。

已核对的复用基础包括：

- [RunRepository](../../apps/desktop/src/main/run-repository.ts)：运行列表与详情入口。
- [RunReadContext](../../apps/desktop/src/main/run-read-context.ts)：父链读取、来源完整性与详情投影。
- [compareRunsEndpoint](../../apps/desktop/src/main/compare-endpoints.ts)：不依赖 Electron 的只读运行比较端点。
- [workspace-view](../../apps/desktop/src/main/workspace-view.ts) 与 [包层 read-api](../../packages/replay/src/workspace/read-api.ts)：检查点清单、附件校验和历史文件读取。

这些模块提供复用基础，尚不是公开稳定的 MCP API。实际设计时提取必要的查询服务和数据类型，让桌面 IPC 与 MCP 调用同一实现；不复制 JSONL 解析、父链拼接、路径判据或附件读取逻辑，也不让 MCP 依赖渲染层 store。共享层放置位置与打包方式按依赖审查确定，不先建设通用插件框架。

完成判据：确定一个客户端和一条本地启动路径，列出数据目录选择、接口版本、查询边界、共享模块迁移范围和失败状态。正文数据返回给客户端后，可能进入其配置的模型服务；配置说明须明确这一边界，不能沿用“数据不会离开本机”的绝对表述。

## 4. MCP1：只读诊断首版

### 代表任务

用户在客户端提出：“找到最近一次失败运行，查看出错步骤，与指定修复分支比较，说明改动和结果，并给出来源。”服务返回已记录事实及定位引用，客户端据此分析；分析结论不写回为原轨迹事实，也不自动认定根因。

### 候选工具与返回范围

以下名称仅用于规划，不作为已发布接口承诺。

| 候选工具 | 返回内容 |
|---|---|
| `list_runs` | 按条件筛选的运行摘要、明确的终止状态、列表读取失败项与分页信息；“出错终止”与用户判定的任务失败分开 |
| `get_run` | 指定运行的摘要、父分支关系、来源完整性、步骤索引及已有消耗事实 |
| `get_step` | 指定运行／span 的已记录输入、输出、工具参数、结果和错误；继承步骤标明原所属运行 |
| `compare_runs` | 指定运行的可比较事实、干预和结果差异；只使用已验收的比较能力，不按序号猜测对应步骤 |
| `inspect_checkpoint`／`read_checkpoint_file` | 指定历史检查点的文件清单／可用性，或按需读取的文件内容；比较文件时明确两侧运行与检查点 |

先返回摘要和索引，正文按需读取。查询须有输出容量上限、分页或续读机制，明确截断和下一步定位；不默认把整条轨迹及全部文件一次塞入客户端上下文。成功结果携带适用的 run、span、检查点和逻辑路径引用，错误携带结构化原因。

### 数据与行为边界

- 服务仅访问显式配置的数据目录；请求使用经过校验的运行标识、检查点和逻辑路径，不接受任意宿主绝对路径。敏感字段处理、正文返回范围及客户端可见错误在提案中明确，不假设已有 trace 已彻底脱敏。
- 复用现有来源与附件校验，区分父链缺失、记录损坏、版本不支持、附件缺失／损坏、二进制和内容截断。缺少的历史状态不回读当前源目录补齐。
- 运行中的记录标明读取时点和未完成状态，读取失败不得呈现为空运行或成功结果；首版是否支持在途读取由设计确定，不承诺实时订阅。
- 查询不触发模型、外部工具、导出或重跑，不修改 trace、附件或源目录。轨迹或操作记录中可核查的失败才能作为失败事实返回，未知原因保持未知。
- MCP 返回只读事实不产生 ReBaseAgent 的模型调用费用；客户端对这些内容进行分析的费用由其自身配置决定。

### 完成判据

在选定客户端完成代表任务，分析引用能回到真实运行、步骤和检查点；核对相同对象在桌面与 MCP 中的事实一致。覆盖非法标识、损坏记录、缺失父链／附件、二进制、长输出、空列表和中断连接等适用场景，记录既有数据不变。另一位使用者能依接入说明配置成功；未通过时先修复支持路径，不扩展客户端数量。

## 5. MCP2：测试证据查询 ✅（2026-10-26 实施并验收；随 `v0.7.0-rc.1` 发行）

在 MCP1 基础上查询 R3 实际记录的命令、参数、工作目录、stdout／stderr、退出码、耗时、环境版本及相关产物。每条证据对应实际 run、检查点和执行身份；日志按范围读取，并保留截断说明。

区分测试断言失败、启动失败、环境准备失败、超时、取消、崩溃及未知状态。缺失测试记录不能返回“测试通过”，一次通过也不表示完整正确性。历史运行没有的环境或日志不事后补造；材料包导出与此查询能力分开验收。

完成判据：客户端能从原失败分支追到修复分支的实际测试和文件产物，核对命令及可比较环境；缺项与错误分类在桌面和 MCP 中一致。此阶段仍只读，不允许借查询执行命令。

**状态（2026-10-26）**：已完成验收——`list_verifications`/`get_verification`/`read_verification_log`/`inspect_verification_artifacts`/`read_verification_artifact`/`compare_verifications` 六个只读工具，十三工具发现；WorkBuddy 5.9.2 真实客户端回查与桌面同对象一致，真实数据根零写入指纹实测。**已随 `v0.7.0-rc.1` 打包**：发行 zip 的 `mcp/` 为十三工具版本（`v0.6.0-rc.1` 及更早为七工具）；外部客户端在 0.7 发行包上的重跑仍待回填。证据：`openspec/changes/archive/2026-10-26-add-mcp-verification-evidence/evidence-index.md`；接入见[只读诊断指南 §5b/§10](../guide/mcp-readonly-diagnostics.md)。

## 6. MCP3：受控执行入口

只在真实使用证明需要“分析后直接执行”时单独立项，首版选一个已有操作，例如隔离 prompt 单分支实验。结果编辑续跑沿用既有轮末语义；修改工具参数后真正重做须等待 R4，二者不能共用含混的“重跑”承诺。

设计至少明确以下契约：

- 先预检并提供计划，说明输入修订、基线、模型、实际工具／测试范围、费用与副作用边界；执行授权绑定具体计划和本次操作，计划或输入变化时失效。客户端的工具调用或只读会话不能自动代替必要的确认。
- 通过共享执行协调入口复用来源校验、操作登记、去重和单执行槽。若采用独立进程，须先解决桌面与 MCP 跨进程协调，不能各自创建一个独立 registry 就声称全局去重成立。
- 发起后返回可信操作 ID，以实际状态和结果 run 关联查询；断线、超时或客户端重试不能重复发起，未知状态先核对。请求受理不等于运行成功。
- 取消只在实际停止执行的路径开放；失败保留真实记录和原因。MCP 不直调任意 handler、宿主 Shell 或绕过已有隔离入口。

完成判据：在选定客户端完成一条“预检／确认 → 执行 → 查询 → 比较”的流程，覆盖重复提交、断线重试、过期计划、费用／写入确认、并发占槽和失败结果定位。需要取消的操作须证明执行实际停止；没有对应能力时不发布取消接口。

## 7. 实施与文档交付

每个 MCP 阶段形成独立 OpenSpec 提案；MCP0 与 MCP1 可在范围明确后合并为一个实施单元。交付内容包括接口与错误契约、客户端／服务版本、安装启动和数据范围说明、相关代码验证、真实客户端验收及已知限制。新依赖的运行时、发行体积和许可证按既有发布流程核对，不预先承诺随桌面包捆绑或具体发布日期。

本次仅建立规划并同步文档；没有新增 MCP 使用指南、安装配置示例或可调用工具，避免将候选接口写成已可使用。主线及阶段交付状态见[项目状态](../development/project-status.md)，实施拆分映射见[能力细化稿附注](2026-10-12-capability-roadmap-from-r2-2.md#13-2026-10-18-附注mcp-服务实施映射)。
