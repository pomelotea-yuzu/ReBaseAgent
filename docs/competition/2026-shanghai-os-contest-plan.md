## 三、评审对齐策略（4 维度 → ReBaseAgent 怎么打）

### 1. 技术创新 30% —— 主打"调试范式的独创性"
- **核心论点**：对 Agent 而言"上下文即程序"（system prompt=源码、消息历史=运行时、tool_result=输入）。展示如何定位错误上下文、修改工具结果并在隔离文件状态中续跑，验证输出变化。
- **独创机制（逐条可证伪）**：
  - 时间旅行最小切片：改某步 `tool_result` → 从该步重跑；分叉点前**本地拼接复用（零 API 调用）**，分支点后真调；provider 前缀缓存是否命中以实际用量为准。历史案例记录的“3 调用改最后一步、1 次新请求、484 输入命中 256、成本为父运行的 21%–40%”须核对原始证据及计费条件后才能引用，不预设参赛案例有相同收益。
  - 隔离文件重跑（COW 副本世界）：带写工具的 run 也能"退回重跑"，父/源/兄弟逐字节不变。
  - Trace-as-Test：封存 trace 当卡带，用当前 agent-loop 零网络零模型费用重跑；是包 API/CLI 能力，可进 CI，不能描述成 exe 内已有操作。
  - 本地优先：轨迹与文件附件本地保存，真实模型请求仍按用户配置发往服务商。
- 同类比较以核实的产品版本、部署方式和能力为依据，不笼统宣称竞品只读或必然出境；未完成调查时以本项目可复现机制说明创新点。

### 2. 场景落地 30% —— 主打"可部署、可运行、可测试、场景真实"
- 可部署：Windows x64 便携 exe **<100 MB**，双击即用、不写 AppData/注册表；数据在 exe 旁 `data/`，可整文件夹带走。
- 可运行/可测试：在参赛基线上运行 `pnpm check:ci` 与桌面构建、实包验收，记录日期、提交、实际测试数及结果；Gitee Go 运行结果与本地检查分别记录，不沿用旧的“1802+ 全绿”作为新包证明。
- 场景真实：用真实模型执行可公开的文件任务，记录原始结果、修改、续跑和修复判据。受控示例明确标注；AniPedia 的 trace 接入记录不能自动当作该项目已完成隔离文件修复的证据。
- **视频主线为“文件出错 → 定位 → 改一步 → 隔离续跑 → 核验文件变化”**。缓存与消耗为辅助证据，不把省钱作为必须出现的演示结局。

### 3. 开源治理 20% —— 主打"协议合规 + 文档规范 + 治理意识"
- MIT 协议；整理实际依赖与许可证说明，不以“零厂商 SDK”推导依赖合规。
- **Spec-Driven Development**：OpenSpec 管理，能力按 proposal→评审→实现→验收→归档推进；主 spec 和归档 change 数量在参赛基线重新统计。
- 文档规范：以 Gitee 可访问的 README、openspec、各 change design.md 和贡献说明为证据；本地未入库的 HANDOFF/docs 不直接当作公开仓库材料。
- 新项目看规划 → 需补 **CONTRIBUTING / 治理说明 / roadmap**，体现贡献与治理意识（目前是个人项目，写清规划即可）。

### 4. 长期发展 20% —— 主打"清晰迭代记录 + 路线图 + 可持续"
- 从 MVP(v0.1.0)→v0.2.0→V3a/V3b→A1/A2/A3/A4→v0.3 体验包，迭代脉络清晰可查。
- Roadmap：隔离 A/B/C 已归档，本轮目标完成 U1–U8；后续实际项目接入、结果导出和单环境测试按[隔离重跑路线](../engineering/plans/2026-09-16-isolated-rerun-roadmap.md)推进，多平台按反馈排序，不把已完成 C 段重新列为待开发。
- 单人项目的可持续性：说明本地优先卖点、MIT 社区友好、后续多平台与社区计划。

## 五、演示视频方案（核心功能 + 使用流程）

**建议时长** 3–5 分钟，中文解说或完整字幕，录 Windows 便携版真机操作。该时长是制作建议，赛事另有规格时按官方要求调整。

**正式录制节点**：U1–U8 全部完成并验收，新参赛包通过实包验收及案例彩排后录制，目标 10/04–10/05。U2 后的 K1 可用于内部验证和素材试拍，不安排为本次正式参赛成片；无需等待导出、真实测试或全部后续产品路线完成。

分镜脚本（待细化）：
1. 开场（约 30s）：展示文件任务、错误产物和预先确定的正确性判据，点明“Agent 的时间旅行调试器”。
2. 定位与修改（约 60s）：打开已有隔离文件运行，找到相关步骤和工具结果，编辑并核对续跑范围。创建入口使用“隔离文件运行”；普通原生纯对话运行没有工具，不能代替本案例父本。
3. 隔离续跑（约 60s）：提交真实模型执行，展示等待、结果落点和新分支。等待可加速或剪辑并注明；预录结果不可伪装为刚执行的结果。
4. 验证结果（约 60s）：通过已验收的运行对比与文件检查点说明变化，按判据判断修复，附源目录/父/兄弟未变的核验依据。文件 diff 两侧按实际检查点解释，不宣称任意跨运行文件 diff。
5. 机制与结尾（约 30–60s）：解释前缀复用、隔离文件状态、本地轨迹保存和模型请求边界，给出 Gitee 与参赛版本。预算地图、缓存只在有助于解释时展示；模型 A/B 和 Trace-as-Test 放 PDF 或补充片段。

保留原始录屏、完整 trace/附件副本及核验记录；公开视频不含凭据或私人数据。受控案例需标明来源。投稿成片与后续 30–60 秒社区短版可共用素材，但不让短版制作阻塞 10/07 参赛提交。

> **录制方式**：你本地录屏最稳（OBS/系统录屏）。我可尝试用 CDP 自动驱动便携版截图/录屏，但带音频的解说仍需你补。先出脚本，录制你定。
