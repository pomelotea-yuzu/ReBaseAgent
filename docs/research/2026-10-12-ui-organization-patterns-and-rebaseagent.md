# 跨品类软件的 UI 组织逻辑与 ReBaseAgent 收敛方向（调研存档）

日期：2026-10-12。状态：官方资料调研与现状结构分析已归档，未做交互原型或实现。后续实机观察单列在[走查记录](../reviews/2026-10-12-ui-live-walkthrough-and-refinement.md)，不改变本轮资料调研的方法口径。

问题起点：维护者在当前版本已经感到 UI 臃肿、内容位置混乱。本稿调查开发、API、数据库、工作流、Notebook、日志／性能分析、CI 和专业创作软件，研究它们如何组织对象、导航、操作和执行结果。

关联：[能力增强路线草稿](../product/2026-10-12-capability-roadmap-from-r2-2.md)、[竞品与社区调研](2026-10-12-agent-differentiation-and-community-needs.md)。本稿聚焦当前信息架构，新增能力仍从 R2.2 规划；现状 UI 问题按新的设计／变更处理，不追溯增加已归档阶段任务。

## 1. 调研结论

**优先研究“每类内容应该固定在哪里”，再调整按钮、留白和折叠。** 调研中的专业软件通常给对象导航、主内容、局部操作、运行状态和技术详情分配相对稳定的位置。功能可以很多，用户仍能根据当前对象判断下一步去哪里。

对 ReBaseAgent，建议优先验证“以一次运行为中心的工作区”：查找／选择运行后，在明确层次里查看结局、步骤和文件；修改、实验、比较是围绕该运行开展的任务，来源和结果始终可追踪。顶栏承担应用级入口与简短后台状态，当前对象的身份和动作归其工作区。

这是设计建议，尚未证明哪种布局最适合本项目。竞品也会臃肿，官方文档描述某种布局不等于它有更高可用性；需要同任务找内容测试来选择方案。

## 3. 九种软件的组织逻辑

### 3.1 IDE：VS Code——给不同区域明确职责 [U1–U2]

**文档事实：** Activity Bar 切换导航视图；Primary Side Bar 承载文件、搜索、版本管理等导航；Editor 承载当前文件；Panel 承载终端、输出、问题等；Status Bar 提供状态。支持编辑器分组、布局恢复与专注模式。当前文档也有 Secondary Side Bar，默认内容和显示方式依场景而变化。

**组织逻辑：** 区域按职责分类，文件在主内容区打开；操作围绕当前编辑对象。窗口布局和当前文件是两个可分别保持的状态。

**可借鉴：** 给导航、正文和后台输出稳定位置；从正文能知道当前对象；局部工具跟随对象。**不直接照搬：** 多级侧栏、无限标签与完全自由停靠会增加本项目的学习负担。

### 3.2 API 客户端：Postman——对象集合、编辑与执行上下文 [U3–U4]

**文档事实：** workspace 管理工作范围；sidebar 区分 Items、Services、History、Local Files，并支持自定义条目；对象在主区标签打开；预览标签可被下次选择替换，修改状态有提示；环境选择器定义请求环境；右侧栏提供评论、代码片段、请求信息等局部工具。支持 `Reveal in Sidebar`、标签搜索和命令面板。

**组织逻辑：** 稳定保存的请求与历史访问有不同位置；选择请求、查看内容、编辑、执行均保留对象上下文。辅助信息以所选对象为条件出现。

**可借鉴：** 原始运行／调用与修改草稿分别标记；编辑页显示来源；环境／模型配置与目标对象配对；从详情反向定位导航。**不直接照搬：** 顶栏的团队、服务、计划和协作入口与当前单维护者工具不匹配；Postman 自身也有大量导航功能。

### 3.3 数据库工具：DBeaver——对象树、编辑器与活动对象 [U6、U29]

**文档事实：** Connections 树组织 connection、schema、table 等对象；点击对象进入对应 editor／viewer。可以按 Simple／Advanced／Custom 控制树中细节，`Link with editor` 反向定位活动对象。主区域包含 views 与 editors，只有一个活动对象；工具栏可用项跟随活动 editor 改变；窗口可以收起、最大化和恢复。

**组织逻辑：** 导航回答“对象在哪里”，编辑器回答“它是什么／怎样处理”，工具栏回答“现在能对它做什么”。后台对象关系不必全部铺到正文。

**可借鉴：** 运行、步骤、文件的身份层次；从文件／错误跳转后在目录显示其位置；随当前对象改变操作。**不直接照搬：** 全数据库树与复杂视图停靠；也不为保持树结构而强行新增项目／连接管理。

### 3.4 工作流工具：n8n——流程定义与某次执行分开 [U9–U10]

**文档事实：** workflow 是连接的节点集合；execution 是 workflow 的一次运行。既有全局 execution 列表，也有当前 workflow 的 execution 列表；文档单独介绍查看、筛选、调试和重跑历史执行。它区分手动与生产执行。

**组织逻辑：** 可修改定义与已经发生的运行有不同身份。调试历史结果需显式进入对应执行，避免把历史状态和当前编辑内容混为一体。

**可借鉴：** 历史运行保持事实，修改进入明确的新草稿／实验流程；后台执行完成后有具体结果位置。**不直接照搬：** ReBaseAgent 没有任意工作流编排能力，不能把分支树包装成可编辑节点画布。

### 3.5 Notebook：JupyterLab——活动文档与后台执行独立 [U11、U16]

**文档事实：** main work area 打开文档与活动；左侧有文件、活动／运行列表和目录等，右侧有属性检查器与调试相关内容。当前活动明确标记；workspace 保存打开对象与布局。Simple Interface Mode 专注单个活动，退出恢复布局。关闭 notebook 不会自动停止其 kernel，Running 面板可以查找与停止后台 kernel／terminal。

**组织逻辑：** 当前读写内容、持久文档状态、后台执行是不同维度，用户切页时仍能找回运行对象。

**可借鉴：** 保留已有草稿与执行身份管理；提供稳定活动入口，关闭详情与取消执行明确区分。**不直接照搬：** 用多个空面板同时展示这些维度；后台活动入口只展示实际状态，并保持结果可到达。

### 3.6 日志分析：Grafana Explore——按查询任务组织主区 [U30]

**文档事实：** Explore 作为查询、分析、聚合数据的起点，用户无需先建 dashboard。官方概览把 query management、query inspector、logs、traces 和 correlations 分成对应内容入口。

**组织逻辑推断：** 临时调查围绕当前查询和数据展开，技术检查内容有自己的层次；“我要查什么”优先于先建一套展示面板。具体数据源、时间范围与分屏交互需补读相应页面，本轮不把这些细节当成已完成核查。

**可借鉴：** 为找错误、找文件、找步骤提供明确的查找范围和结果定位；先支持临时调查再考虑保存复杂分析视图。**不直接照搬：** dashboard 体系、查询语言编辑器或分析图表堆叠。

### 3.7 性能分析：Perfetto——全局概貌与当前选择 [U15]

**文档事实：** trace 在时间轴中查看；点选事件后在 `Current Selection` 抽屉显示详情；track finder 搜索轨道，筛选是非破坏性的；可以固定轨道、收起详情抽屉，并在同轨道相邻事件之间导航。

**组织逻辑：** 大规模数据先通过概貌与筛选缩小范围，详细属性跟随选择出现。查找、选择和检查保持明确关系。

**可借鉴：** 先定位异常步骤，再看完整输入／结果／技术字段；比较与定位保留当前选择。**不直接照搬：** 默认用时间轴代替 Agent 的调用顺序，尤其没有真实时间戳的导入数据不能生成精确时间关系。

### 3.8 CI：GitHub Actions——执行、作业、步骤、日志的层次 [U27]

**文档事实：** 每次 workflow run 包含 job，每个 job 包含 step；可查看结局、耗时、失败步骤日志，复制日志行链接，下载日志和产物。文档指出日志搜索只覆盖已展开步骤；部分重跑日志归档只包含被重跑 job。

**组织逻辑：** 先看这次执行的结果，再进入失败位置，最后看详细日志；下载材料明确它覆盖哪一次／哪些部分。

**可借鉴：** 概览明确失败与定位入口，步骤承载事实详情，产物与来源关联；搜索／导出范围必须可见。**不直接照搬：** 将所有工具错误当作最终失败原因，或把一次 Agent 运行强行套为 CI job 模型。

### 3.9 专业创作：Blender——同一项目按任务切换布局 [U25–U26]

**文档事实：** 窗口分 Topbar、Areas、Status Bar；workspace 是面向 modeling、animation、scripting 等任务的预定义布局，每个布局由不同 editors 组成。布局可保存，workspace 可记录场景与模式设置。

**组织逻辑：** 同一批对象可以在不同任务中用不同布局处理；任务切换不是创造另一份数据。

**可借鉴：** 查看、编辑、比较可有不同布局，但保留明确对象和返回路径。**不直接照搬：** 每项能力建一个长期一级 workspace 标签，或照搬繁多模式；这会让入口数量继续增长。

## 4. 跨品类模式对照

| 模式 | 代表案例 | 解决的问题 | 对本项目的启发 |
|---|---|---|---|
| 对象导航 + 主内容 + 辅助检查 | VS Code、DBeaver、Postman、JupyterLab | 找对象、看内容、做局部操作 | 给运行／步骤／文件明确层级与反向定位 |
| 定义／草稿 + 执行历史 | n8n、GitHub Actions、JupyterLab | 编辑状态与发生过的事实混淆 | 历史、草稿和新 run 的身份持续可辨 |
| 概貌／筛选 + 当前选择详情 | Perfetto；Grafana 的查询任务定位 | 大量记录中的调查负担 | 先缩小范围，再展示详细证据 |
| 同一对象 + 任务布局 | Blender、VS Code 专注布局、JupyterLab 简单模式 | 在编辑、查看、比较中争夺空间 | 少量明确模式，保存对象与阅读位置 |

上述模式可以组合。这里并不证明“两栏永远比三栏好”或“折叠越多越清爽”：频繁定位需要并列导航；频繁编辑需要正文空间。决定默认布局应看任务频率和实际寻找成本。

## 5. 对当前 ReBaseAgent 的结构分析

以下是代码事实及其风险推断，尚不是本轮实机测量结论。

| 当前代码事实 | 可能带来的寻找负担 | 调研启发 |
|---|---|---|
| [GlobalBar](../../apps/desktop/src/renderer/src/components/GlobalBar.tsx)同一区域组合视图切换、当前 run ID、Operations、会话草稿、新建、录制、代理状态与运行配置 | 用户需要先判断按钮作用于应用、当前 run、后台任务还是某个草稿；多个概念同级竞争注意力 | 应用导航、对象动作和后台状态分工 |
| [RunHeader](../../apps/desktop/src/renderer/src/components/RunWorkspace.tsx)又呈现任务、状态、ID、模型、隔离／来源信息；顶栏也呈现 run ID | 同一身份重复占位；全局身份与当前主内容对象的关系需要辨认 | 一个明确对象头，完整技术字段按需查看 |
| 顶栏“轨迹”是应用 view；运行内有“步骤”tab；[SpanTree](../../apps/desktop/src/renderer/src/components/SpanTree.tsx)目录标题也叫“轨迹” | 用户难以从名称区分整体布局、运行内容类型和步骤目录 | 先定义命名层级，再调整位置 |
| [RunList](../../apps/desktop/src/renderer/src/components/RunList.tsx)每条记录包含状态／来源／任务、短 ID／分支／模型、时间／步骤／工具／错误／token／缓存／耗时 | 快速找任务时，需要扫过大量与当前查找目标无关的信息 | 默认突出身份与结局，次级指标按需显示；设计时保留未知／来源语义 |
| 运行列表搜索覆盖任务／ID；分支树也搜索运行；文件页有文件范围查找，正文有各自编辑器查找 | 搜索入口存在，但用户要先猜“这类内容属于哪里”；尚不能等同为跨错误、工具输出、文件内容的统一搜索 | 搜索明确范围，结果带运行／步骤／文件定位 |
| [App](../../apps/desktop/src/renderer/src/App.tsx)存在 run 内容页与 create、recording、experiment、messages、compare 等工作区；辅助页有[返回来源](../../apps/desktop/src/renderer/src/components/AuxWorkspaceFrame.tsx) | 多个任务会替换主内容，需要记住所在对象、来源和返回目的地；笼统“来源”需要上下文解释 | 明确任务标题与对象路径，保持草稿、阅读与返回目标 |
| 分支树是全局视图；运行比较、指标对照、双运行正文有独立呈现 | “看分支关系”“选比较对象”“比较结果”可能需要切换多种理解方式 | 区分关系视图、选择动作与比较内容；入口靠近当前对象 |

已有可用性成果应保留：文件页不常驻步骤目录、按 run 保存阅读状态、草稿恢复、来源缺失时诚实降级、操作结果关联、详细说明展开和专注模式。10/10 复查解决了局部页头占位与编辑器问题，但没有以维护者寻找内容的任务证明整个信息架构已经清晰。

## 6. 建议验证的 UI 逻辑

### 6.1 先固定五种信息的归属

| 类型 | 例子 | 建议固定位置 |
|---|---|---|
| 应用级能力 | 新建、录制接入、设置、应用范围查找 | 简短全局入口；设置与接入各有可到达位置 |
| 当前对象 | 哪次 run、哪个步骤、哪个文件、哪两个比较对象 | 主内容区对象头／路径；技术 ID 可复制，避免多处重复 |
| 当前对象内容 | 结局与输出、步骤事实、文件状态 | 运行内的稳定内容导航，名称与作用层级一致 |
| 当前任务动作 | 改指令、改工具结果、重跑、比较、导出 | 对象级工具区或就近动作；运行前确认实际目标与执行范围 |
| 临时／后台状态 | 草稿、在飞操作、结果通知、代理异常 | 稳定活动入口及就近异常；具体条目可定位对象，关闭页面不等于停止执行 |

这里的“应用范围查找”是候选能力：当前运行搜索可先迁入一致入口，跨正文查找需要定义索引、性能与数据范围，不能只加一个看起来能搜全部的框。

### 6.2 用运行作为日常定位锚点

候选对象结构：

```text
运行记录
  └─ 选定一次运行
       ├─ 结局／输出（现有概览的任务）
       ├─ 步骤 → 选定调用 → 输入／结果／局部编辑
       ├─ 文件 → 检查点 → 文件内容／差异／导出
       └─ 相关分支与比较（围绕明确来源）

新建／录制：应用入口
修改／实验：显式绑定来源对象的任务
草稿／执行活动：可定位上述对象的会话状态
```

这只表达信息归属，不预先决定增加四个页签或改变现有 tab 名称，也不要求新建项目数据模型。可以先保留“概览／步骤／文件”，让分支与比较通过对象级操作进入。

### 6.3 少量任务布局，保持同一来源

查看态突出结局与定位，编辑态突出原值与草稿，比较态突出两侧对象与差异。每种模式都有明确身份与退出位置；打开辅助任务不需要先理解另一套导航体系。

独立大页面仍适合复杂表单和双侧编辑。小确认与简单参数适合局部展开。选择依据是内容长度、阅读空间、草稿寿命和任务频率，不能把所有辅助页强行压成抽屉，也不无限新增长期标签。

### 6.4 折叠有边界

完整 ID、快照/profile、技术配置、详细指标、长期解释可以按需展开。当前对象、运行结局、实际执行范围、未保存修改、计费确认和需要处理的失败不能仅靠隐藏说明表达。

未知数据与缺失来源仍要诚实；可以减少重复信息，但不能隐藏影响用户判断的事实。不可用操作的原因应可达，具体常驻或按需位置需要结合现有规范设计。

## 7. 两个候选整理方案

### 方案 A：保留当前工作区，重新分工与命名（建议先验证）

保留现有运行导航与概览／步骤／文件框架；区分顶栏的应用入口、当前 run 动作和活动状态。运行列表默认突出任务、结局、时间与必要短标识；详细消耗仍可查看。统一“轨迹／步骤／分支关系／比较”等名称的层级，辅助页显示具体来源与返回目的地。

优势判断：能复用当前阅读、草稿和执行状态，结构迁移较小。风险：如果主要问题来自多工作区跳转，只整理顶部与列表可能改善有限。

### 方案 B：运行中心的统一任务外壳（后续原型比较）

日常查看有稳定对象头和主内容导航；进入编辑／实验／比较时，在统一外壳中改变任务布局并保留来源，当前相关目录按任务出现。运行列表与步骤目录是否同时显示可有不同默认，保留用户显式展开能力。

优势判断：上下文和任务层次可能更统一，也能承接 R2.2 以后能力。风险：需要处理全部返回、草稿、焦点、来源失效和后台操作情况，变更成本更高；若增加一层导航，可能让寻找更慢。

先用同任务原型比较 A、B，再决定结构。两栏／三栏、抽屉／独立页面属于布局选择，无法单凭调研决定。

## 8. 同任务找内容验证

使用同一批已录制测试资料，不实际请求模型。比较当前界面与候选原型，任务包括：

1. 找到某次失败运行，指出真正的终止原因并进入对应调用。
2. 查看该调用时可用的文件状态，确认当前检查点和文件来源。
3. 找到之前未提交的草稿，切到另一页再返回，说明编辑对象。
4. 找到父运行与修复分支，比较输出与文件，返回来源位置。
5. 执行详情关闭后，从活动入口找回该操作状态及结果。
6. 找到一条工具输出中的文本，判断搜索覆盖了哪些记录；未支持全局正文搜索时明确记为能力缺口。
7. 为选定检查点找到导出入口，确认实际目标与产物范围。

记录首次定位时间、错误入口次数、返回路径、能否说出当前对象、是否混淆当前模型配置与历史事实，以及任务完成率。窗口宽度、辅助栏开合和测试资料一致；窄窗与 200% 缩放另列。维护者自测与新使用者测试分别记录，不把熟悉度差异误当布局收益。

可检查的设计约束：

- 每个入口可以归到“应用、对象、任务、后台活动”中的一个明确角色。
- 正常查看运行时，重复的完整身份信息有明确消除方案。
- 主要内容在常用窗口下可直接到达；路径长度预算通过原型确认，不预填实测数值。
- 搜索与过滤显示范围，隐藏当前对象时保留提示和找回方法。
- 新增 R2.2／R2.3 不各增加一套平行导航；实际执行许可与记录边界保持原契约。

## 9. 与后续能力路线的关系

维护者已反馈当前寻找混乱，因此建议在 R2.2 桌面方案定稿前，先完成现状找内容任务和小范围信息架构原型。包层可行性仍可独立调查；用户界面的入口与层次应以本轮验证结果为依据。

这是一项新的 UI 设计工作，并不重开 U1–U8。改动顶栏、入口、页签或返回规则时，需要同步受影响的 OpenSpec；调研报告不直接改现有组件或放宽来源／执行门禁。

后续能力按同一对象体系承接：R2.2 的指令实验属于来源运行的干预任务；R2.3 的双臂属于同基线的比较任务；R3 测试记录属于具体运行／产物证据；R4 参数修改属于选定工具调用；R5 适配设置属于接入，诊断结果属于对应数据对象。每项新增能力都要说明入口、结果位置与返回对象。
