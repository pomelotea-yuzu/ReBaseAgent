# ReBaseAgent 独创性方向、竞品与社区需求调研（调研存档）

日期：2026-10-12。状态：第一轮公开资料调研已归档；候选能力未立项。2026-10-12 本轮调研到此收束，保留后续验证事项。

本地参考提交：`cbb5b7dab975088bd4c7d5a02d6ed60dba70c43f`。能力与排期依据[产品演进路线](../product/evolution-roadmap.md)，R2.1 实现边界依据[归档提案](../../openspec/changes/archive/2026-10-12-export-run-results/proposal.md)。本文提出候选方向，不修改现有执行门禁或路线排序。

## 1. 当前判断

**值得争取的方向是：让开发者能解释一次失败、验证一次干预，并把实验交给别人复现。** 普通轨迹查看、时间旅行、prompt A/B、本地会话导入、费用统计和导出已有成熟先例，不能单独作为独创性主张。

优先研究三个问题：

1. **上下文与文件状态是否一致？** 恢复了消息，却没有恢复对应文件；有文件快照，却缺少真正发给模型的输入。系统应具体指出缺了什么、能做什么、不能做什么。
2. **修复究竟改变了什么？** 从相同文件起点分别运行，只改变一项干预，连接首次可确认差异、后续文件结果、执行结局和真实消耗。
3. **能否把长失败运行缩减成可复现案例？** 在受支持的执行范围内，寻找仍然保留失败的输入与文件集合，并交付能够再次验证的材料。

三项均为**原创性候选**，不是“已证明首创”。检查点、内容寻址、实验对照、差异分析、delta debugging 均有既有技术；需要验证的贡献是它们在 Agent 消息、文件世界、人工干预和执行证据之间的具体契约与体验。

## 2. 方法与证据边界

本轮联网读取了官方文档、项目 README 和公开 GitHub Issue，补充了[09/27 竞品调研](2026-09-27-agent-debugging-landscape.md)。来源编号和 URL 见 §9，日期、正文指纹、引用摘录和 Issue 元数据见[证据记录](2026-10-12-agent-differentiation-evidence.json)。网页和 README 会变动，指纹用于识别本次读取内容，不是软件版本锁定。

- 官方文档／README 能证明作者描述了该能力；不能替代安装后行为验证。
- Issue 是报告者的使用问题或提议，不是本轮复现结果。已关闭的报告用于了解问题类型，不能据此说竞品目前仍有该缺陷；关闭也不自动证明功能已实现。
- 先做关键词检索，再补充标题检索，通常每个查询取评论数排序前 5 项；人工选择与问题相关的条目。该方法偏向活跃讨论，遗漏低热度需求，不能据命中数或评论数推断市场规模。
- 读取的是所选 Issue 的正文与元数据，**未系统阅读讨论回复、关联修复提交或维护者结论**。维护者规划条目与独立用户报告分别标注。
- 本轮未安装竞品、未运行跨产品基准、未访谈社区使用者。论文、研究原型和商业产品扩展也未穷尽，尚不足以证明全球新颖性。

### 对既有导入草稿的校准

[10/11 外部会话导入草稿](2026-10-11-external-agent-trace-import-findings.md)提供了有价值的本地探针记录，但其中“无人提供好用查看器”“竞品没有”“零门槛”不是已建立的竞争结论。[S8–S9、S14、S16] 已提供反例。该旧稿保留当时记录，本稿补充后续核查。

后续仍可做导入，但应以**数据质量、来源可追溯、长会话诊断和支持范围解释**评估价值。缺失 token 应显示未知，不能把源中 0 一律当作真实零消耗；截断消息、合成请求和跳过侧链都应标注。能转换并被 schema 接受，不等于完整还原运行，更不自动获得重执行资格。

## 5. 候选独创性能力

### A. 上下文与文件状态的一致性检查（优先技术验证）

场景：用户打开一个原生分支或导入会话，想知道“这里能否安全继续实验，恢复的是不是同一份世界”。

最小范围：基于已记录事实，列出启动／续跑消息来源、完整性、配对文件快照、工具版本、执行模式与外部状态；输出可查看、可比较、可重发或可隔离续跑的**逐项依据**。同轮末快照不等于工具调用前快照，日志截断不等于真实上下文压缩。缺项时给具体补采集步骤。

潜在贡献：把现有分散在拒绝门禁、阅读降级和导入器中的契约，变成可解释、可导出的诊断结果；在发现消息／文件组合不兼容时阻止错误实验。基础校验是已有机制，新增价值必须由诊断准确性与排障效率证明。

首版避免建设通用“可信评分”。每一结论应有事件／快照引用，未知就是未知；尤其不能通过当前宿主文件补造过去状态。

验证：覆盖原生完整记录、父链缺失、附件损坏、截断请求、缺 usage、轮末／调用前错配；让开发者回答为什么不能运行、需要补什么。若现有错误提示已足够，或对照工具以更少步骤解释同样问题，则缩减范围，不宣称差异优势。

### B. 相同文件起点下的受控修复实验（与 R2.2／R2.3 结合）

场景：开发者怀疑失败来自一项指令，想验证“改这一项有没有改善”，并知道改善以什么代价发生。

最小范围：使用同一初始文件快照与配对启动输入，一次只改一个因素；记录模型／参数／工具版本和人工干预。展示输出、文件结果、执行结局和真实新增消耗；保留失败尝试。实验请求本身不发起模型调用，真实执行仍须走授权与费用确认。

可研究扩展：寻找**首次可确认的观察、操作或文件差异**，并标出匹配依据。跨模型步骤数不同，不能按“第 N 步”强行对齐；不可靠匹配要显示未知。只读／写入关系只能先覆盖固定文件工具，通用 Shell 的文件依赖不可凭命令字符串推断。

潜在贡献：将状态一致性、干预记录、差异定位和实验结果绑定到一条可核查流程。A/B 和首次差异分析本身都不是新概念。不同模型的一次对照也不是因果证明；重复采样、版本变化与基础设施错误必须分别报告。

验证：两个明确失败案例，固定基线，分别比较原方法、普通 A/B 与本流程的定位时间、成功判据、重复费用和帮助次数。若只能提供更多图表却不能改善判断，停止差异分析扩展。R3 未完成时只能依确定性文件规则或人工判据评价，不宣称测试通过。

### C. 将失败运行缩减为可复现实验（研究储备，先设计再估算）

场景：长任务失败，维护者收到几 MB 日志和整份项目，却不知道最少需要哪些输入才能复现。

最小研究对象：固定文件工具与根基线，给定一个确定性失败判据，在独立分支中尝试减少输入文件／任务内容，每次记录是否仍失败和新增成本，输出一个“更小且再次确认失败”的案例。

潜在贡献：在 Agent 的消息与文件配对约束下应用既有 delta debugging；保留失败、干预和所有缩减尝试的来源。不能声称证明全局最小，不能因为工具没有读取某文件就自动删除它，未重新执行的裁剪只能叫诊断摘录。

验证：先用确定性 fixture 验证缩减与恢复不变性，再对有随机性的 Agent 案例进行重复确认，比较手工整理耗时。若生成成本过高、失败过于随机或复现依赖未受支持外部状态，保留人工选择的材料整理，不默认自动缩减。

### D. 可校验、可脱敏的失败材料包（交付支撑）

连接所选事件、人工干预、文件哈希、来源完整性、环境说明与已有执行证据；接收者无需凭据即可只读检查。与 R2.1 的文件产物导出分别定义，R2.1 不自动扩成全 trace 导出。

分享前预览敏感消息／路径／凭据和缺项，脱敏材料注明不可据其完整重执行；证明来源文件和脱敏副本的关系，而非覆盖历史。材料包与收据已有先例 [S9、S16–S17]，潜在差异在可校验的状态配对与恢复边界，不在“导出一个 ZIP”。

### E. 上下文变化与数据质量诊断（可先做只读试验）

从明确记录的压缩事件和真实请求快照，展示哪些文本发生变化、是否截断、工具结果是否缺失。区分“源未提供”“导入器省略”“真实请求没有包含”，成本与耗时同样标明真实／推导／未知。

与 ccx 的 context trace、现有上下文预算地图已有重叠 [S16]。先验证能否帮助定位一种实际错误，不用模型总结代替事实，不承诺恢复未记录请求。未知 usage 统一诚实展示是质量修正，本身不应包装成独创功能。

### F. 从修复实验生成回归用例（R3 之后完善）

保留明确的输入基线、干预、确定性断言和失败分类，形成可重复检查的案例。必须区分录制响应下的 Trace-as-Test、文件状态不变性、真实项目测试、重新调用模型的质量实验，分别说明环境、网络与费用。

promptfoo、Phoenix、LangSmith 的评估／数据集已是成熟参照；差异只能来自本项目对历史文件状态和修复来源的具体绑定，不来自“把 trace 当测试”这一概念。

| R2.3 | 不同模型／参数的隔离实验 | B 的重复采样、失败分类与费用记录 | 普通双臂可提前讨论；完整多臂排序需同步修订路线 |
| R3 | 一个真实测试／构建环境 | B 的执行判据、C 的代码失败判据、F 的项目回归 | Windows 执行隔离技术验证通过后开放，不能退回未约束宿主 Shell |
| R4 | 工具调用前恢复与参数重做 | B 的工具参数干预与更细差异定位 | 现有轮末快照不够，需新采集契约 |
| I／R5 | 真实项目与更多工具状态适配 | A 的具体源诊断、D 的跨项目材料 | 导入查看不等于接管原 Agent 执行，逐源声明支持范围 |

**初步建议：完成 R2.1 后，先验证 A 的诊断价值，再把 B 的最小范围放进 R2.2 提案。** R3 技术验证可独立准备。R2.3 提前与否，按用户是否确实需要多模型实验决定，不以“模型比较看起来新颖”作为理由。C 先作为研究实验，D／E／F 随真实用例安排。

这比单纯串行完成 R2.2、R2.3 更接近目标：每项基础能力都围绕一种可证明的新调试体验建设，而不是仅增加菜单。

## 7. 下一轮验证方案

### 竞品统一任务

固定软件版本、输入、文件内容和可公开失败判据；至少比较 LangGraph + Studio、一个普通 prompt／模型实验方案和 ReBaseAgent。Claude Code 可作为开发者现有排障方法，但需注明工具和引擎不同，不能用单次不同模型输出比较产品优劣。

任务包含：读取后写入、同轮多工具、中途消息干预、初始 prompt 干预、缺失快照、上下文截断、provider 错误。允许对照方案写合理官方适配，单列接入改动、准备时间与执行时间。

记录：能否定位错误；恢复与执行范围是否解释清楚；源目录／父／兄弟分支指纹；首次得到可核查结果的时间；真实调用次数与额外费用；导出材料是否自包含。失败与不支持结果一并保留。

### 社区需求核实

访谈 5–8 位目标开发者作为定性起点，尽量包含 Windows coding Agent 使用者和自建文件 Agent 维护者。人数是工作建议，不是统计代表性。首轮不要展示功能清单，先请对方讲最近一次失败：

- 原来怎样定位，哪一步最费时间，有没有可公开／脱敏材料？
- 是否出现消息恢复而代码不一致、重试重复执行、压缩丢要求、实验偶然通过？
- 已用哪些查看器、检查点和评估工具；为什么仍需另一个工具？
- 想交给同事什么材料，对本地／网络／费用有哪些具体限制？
- 在原任务中使用候选流程后，是否能减少步骤或独立完成？

记录每位使用者的问题、现有替代、实际阻碍和候选能力的否定反馈，不预先要求他们认同方案。本轮没有联系任何人；后续对外提问／邀请另由用户授权安排。

### 继续或停止条件

至少在两个独立真实任务中出现同类阻碍，并能取得足够输入和正确性判据，再考虑升级为能力提案。若现有工具已低成本满足需求，应考虑互操作或适配；若收益主要是 UI 风格，不作为技术独创性主线；若无法约束文件／外部状态，则先保持只读诊断。

## 8. 表述边界与暂缓方向

可作为研发方向表达：“研究消息与文件状态的一致恢复检查”“在相同文件起点下记录单项干预及修复证据”。在实测之前，不说“比竞品更快”“完整恢复任意 Agent”“唯一支持时间旅行”“跨源查看首创”“一次 A/B 证明模型更好”。

暂缓把通用插件平台、多 Agent 调度、自动根因裁决、全语言 Shell、自动最佳模型排名、大量费用图表或更多导入源升级为主线。每项都可能有用，但本轮证据尚未证明它们能优先解决定位与验证问题。
