## 一、产品策略探讨闭环

延续 09-04 晚的方向探讨，今天凌晨收口 + 下午定稿评审。核心文档是 `docs/product/product.md`（"真产品方向，非纯作品集/自用工具"）。

**一句话定位**：*ReBaseAgent 是本地优先的 Agent 调试、实验与测试平台*。内核比喻是 **"上下文即程序（context is the program）"** —— Agent 跑歪时 bug 不在 loop 代码里，而在某一步的上下文（脏 tool_result / 偏 prompt）里。

**四个 JTBD 触发场景**（博客可直接用这张表）：

| # | 用户此刻在做什么 | ReBaseAgent 做什么 |
|---|---|---|
| 1 | Agent 跑歪，不知哪步把模型带偏 | 打开 span 时间线，点每步看模型当时看到的完整上下文 |
| 2 | 某步 tool_result 脏了，想改了看能否挽回 | 改那步 tool_result，从那步重放，只花后半段 API 费（前缀缓存命中） |
| 3 | 想换 prompt/模型，对比新旧谁更好 | 从 step 0 开分支换 prompt，同前缀缓存命中做 A/B |
| 4 | 偶发 bug 只出现一次，要复现/甩给同事 | 导出 trace，精确指到跑歪的那步（未来进 CI 当回归测试） |

**关键架构决策 —— 时间旅行边界（§5）**：replay 默认 **world-free**（不复执行任何工具，直接把录下的 `tool_result` 喂回模型），外部状态（文件/DB/API）不参与 → trace 内自洽，彻底消解「回到某步但文件已变」的不一致。仅显式「真重跑带副作用工具」时才进分支隔离世界（COW overlay / 逐步快照），由 `sideEffect` 标志分级。

**评审定稿的 3 个真问题**（用户问"对定稿有什么意见"后给出，已落地）：
1. **代理与时间旅行的断层（最大暗礁）**：既有 fork 依赖 `tool.invoke`/工具表/`config_hash`，代理录的 run 天然不具备 → 定**方案 a「单请求级最小分叉」**（见第四节）。
2. **信噪比**：代理录全部流量，必须有 source 标记 + 列表过滤 + 可暂停。
3. **「1/4 成本」是理论值**：宣传前须实测拿真数字（现已记入开放问题，降级为待验证）。

> 博客延伸：「为什么不做平台化 / 为什么不做 SaaS 云」—— 本地不出机器卖点 vs 网络效应的张力，是独立开发者做工具类产品最值得写的纠结。

### 🐛 战记：PORTABLE_EXECUTABLE_DIR 陷阱（可直接当博客技术细节）

这是今天修掉的一个**会毁掉核心卖点**的 bug。代码注释把根因讲得很清楚（`apps/desktop/src/main/data-dir.ts` 原文）：

```ts
/**
 * **portable exe 的陷阱**：单文件 portable 版运行时会先把应用解压到系统临时目录再启动，
 * 因此 `app.getPath("exe")` 指向的是临时目录（退出即被清理），而不是用户双击的那个 exe。
 * 数据若锚定在临时目录，每次运行都会丢。electron-builder 为此注入了环境变量
 * `PORTABLE_EXECUTABLE_DIR`（见 app-builder-lib/templates/nsis/portable.nsi），
 * 它才是用户眼中「程序所在的那个目录」。打包后必须用它作为锚点。
 */
```

- **现象**：数据要么写进临时目录（退出即丢），要么弹框让用户选目录 → 便携版完全不可便携。
- **修复**：`resolveAnchorDir({ exeDir, portableExeDir })`，`portableExeDir`（来自该环境变量）优先于 `exeDir`；marker 查找、指针读写、用户选择回写全部锚定到它。`index.ts` 传入 `process.env.PORTABLE_EXECUTABLE_DIR`。
- **验证**：desktop 测试 52→52 全过（data-dir 用例 5→11）；端到端双击 exe 后 `data/traces/` 生成在 exe 旁、Temp 无残留。

> 博客金矿：单文件 exe 本质是「7z 自解压包 + 壳」，`app.getPath("exe")` 在便携场景是个隐藏陷阱，坑过无数 Electron 新手。

- **环境护栏坑**：WorkBuddy safe-delete 按 turn 累计删除数（阈值 50），打包收尾清理 108 MB 中间 7z 被拦。但 **exe 本身已完整生成并签名**，只是中间文件没清。绕开方式：用 `mv` 重命名旧产物目录（重命名不触发护栏），别 `rm`。
- **图标缺口**：仍未设 `build/icon.ico`，分发观感上的明显欠债。

## 四、v-next：LLM 录制代理落地（今天最重的一块）

从 proposal 评审到归档横跨多轮对话，归档在 `openspec/changes/archive/2026-09-05-add-llm-recording-proxy/`。

### 4.1 为什么做（proposal 原文要点）

> 工具类产品最常见的死法是「功能很全、没人装」。当前接入要埋 trace-sdk / 换 agent-loop，改造有成本；目标用户的最低成本动作是**只改一行 `base_url`** —— 把请求指到 ReBaseAgent 起的本地代理，key 一字不动，录制/查看零手工录入。这是把「看 span」入口摩擦降到零的唯一方式。

代理只**观察**请求/响应字节流、**不修改**任何转发内容（转发保真度：逐字节）。录制产物是 trace 内自洽的数据，不涉及工具执行。

### 4.2 设计取舍：我们否决了哪两条路（design D1）

评审确认的断层：既有 fork 依赖 `tool.invoke` 叶子 span / 工具表 / `config_hash`，代理只看到独立 `chat.completions`，三者皆无。候选：

- **a) 单请求级最小分叉（采纳）**：编辑 messages → 代理用暂存 key 重发单请求 → 新 run 记 fork meta。实现比 runLoop fork 简单（无工具编排），且让 JTBD ② 在代理路径成立。
- **b) 代理只看不能改重跑 → 否决**：对 LangSmith 差异只剩「本地」，没护城河。
- **c) 启发式聚合同会话成 run 再走 replay → 否决**：易错、误判不可控。

> 博客角度：这是经典的"我们为什么没选看起来更完整的方案"—— b 太弱、c 太脆，a 最小可用且护城河成立。

**分支视图诚实降级**：`resolveBranch` 保持原样不加 proxy 形态（proxy fork 的 `at_span` 指向 llm.call、编辑的是 messages，没有 replay 层去应用编辑），直接拼接会出现「旧 messages 的 llm.call + 新 messages 的 llm.call」混排假时间线、编辑生效点不可见。故 desktop 对 `fork.edit.field="messages"` 的 run 一律呈现**父链列表**（逐代 run + 编辑摘要，点击切换），诚实且实现最省。

### 4.3 一条贯穿始终的「诚实原则」（可串成叙事）

翻 design.md 会发现一个反复出现的设计取向 —— **不编造、不夸大、状态诚实**：

- **非流式 `ttft_ms` 记 `0`**（design D2 原话）：*"无 TTFT 概念，诚实为零，不拿总耗时冒充"*。
- **流式结束仍无 usage 兜底 `{0,0}`**，与 agent-loop 的 `usage: null` 容错对齐。
- **Non-goals 里"诚实拒绝"**：匹配路径外的端点返回明确 404/501，*不静默透传*。
- **run 状态诚实**：upstream 非 2xx → run 以 `error` 终止；客户端中途断连 → 以 `crashed` 终止（文件无终止事件的自然结果）。
- **key 语义诚实**（design D5）：`keyStore.lastKey` 会被后续请求覆盖，分叉重发用**最新**捕获 key 而非源 run 当时的值 —— 明确接受（key 属于用户应用，ReBaseAgent 只借用不保管），UI 提示语点明。

> 博客角度：可单独成篇 ——《我们造了个比 LangSmith 更不撒谎的调试器》：能改（vs 只能看）+ 本地（vs 上云）+ 指标不造假。

### 4.4 刻意不做的 9 件事（Non-goals，scope 纪律范本）

design/proposal 列了清晰的边界，本身就是好素材：
不做 Anthropic 协议、不做其他端点（/embeddings 等）、不做会话聚合、不做 key 持久化、不做白名单/按模型过滤、不做 HTTPS/多用户/局域网监听、不改既有 replay 路径、不扩展 span 类型、不新增 config.yaml 外的依赖。

> 博客角度：「MVP 之后最该做的不是堆功能，是划清不做什么」—— 这 9 条 Non-goals 是 scope 纪律的正面教材。

### 4.5 评审里的 P0 硬矛盾（config_hash 必填会崩）

用户逐条对代码核实后，揪出一个会直接崩的矛盾：

- **P0**：`RunMetaSchema.config_hash: z.string().min(1)` 必填非空，但代理 run 天然无 config → 照原稿 zod 直接崩。**解法**：config_hash 放宽为 **optional**（存在时仍 `min(1)`）；trace-format delta 增 requirement「无 config_hash 的 run」拒绝作 replay 父本、可作 proxy fork 父本；`task` 口径定死常量 `"(llm-proxy)"`。
- **P1①**：proxy fork 分支视图降级为父链列表（见 4.2）。
- **P1②**：非流式 ttft=0、流式 usage 兜底 `{0,0}`。
- **小提醒全落实**：`source.base_url` = 代理自身监听地址（写死）；llm-proxy 显式声明 `eventsource-parser ^3.0.0`；keyStore「最近捕获」语义写入 spec + UI 提示。

### 4.6 apply 实现 + 冒烟实测数字

- 新包 `packages/llm-proxy`（纯 TS 零依赖）：`createProxyHandler`（路径白名单 404/405/400、逐字节转发、SSE tee 旁路聚合不缓冲整流、key 捕获）+ `startProxyServer`（仅 127.0.0.1、port 0 回读、EADDRINUSE 明确报错）。**默认端口 18787**（8787 与 WorkBuddy.exe 内部服务冲突）。
- desktop main/renderer：ProxyManager、ProxyRunRecorder（span 恒 `s_01/s_02`）、RunRepository 对 proxy run 跳过 resolveBranch、三档过滤、MessagesForkEditor（Monaco JSON）、ParentChainList（降级视图）。
- 门禁全绿：biome 0 errors、四包+desktop 测试全绿（66/52/16/16/62）、双端 typecheck、electron-vite build、validate --strict。commit `2f11409`。

**冒烟实测（真实链路，curl deepseek）**：

| 场景 | 实测 |
|---|---|
| 录制 run（非流式） | 真实 usage **in:5 / out:65**，`ttft_ms=0` |
| 编辑 messages 重发（流式 fork） | **ttft 338ms**，编辑值生效 |
| 空 fork | 禁用 ✓ |
| 无 key 重发 | PROXY_NO_KEY 提示 ✓ |
| 端口占用 | 明确报错 ✓ |
| 老 run「在此重跑」 | 回归 ✓ |

归档：commit `272c72b`，主 spec 新增 `specs/llm-proxy/`（5 requirements），trace-format +2、desktop-ui +4。
