## 三、⭐ 实测一：两模型在这台机器上**不能共存**（你们 §3.2 第 3 条为真）

我直接跑了一遍（本机 Ollama，`/api/generate` + `/api/ps`，跑完已卸载并关停服务）：

```text
载入 qwen3.5:4b  ctx=8192  → /api/ps: qwen3.5:4b   size=3.27GB  vram=3.27GB  ctx=8192   （载入耗时 11.4s）
再载入 qwen3:1.7b ctx=8192 → /api/ps: qwen3:1.7b   size=2.24GB  vram=2.24GB  ctx=8192   （载入耗时  7.5s）
                              ↑ 只剩 1 个：qwen3.5:4b 被挤出
对照：qwen3:1.7b @ctx512 仅 1.29GB；@ctx8192 涨到 2.24GB（KV 随窗口线性涨）
```

**⇒ "两个都预热"在你们这台机器上不可能**，而更要紧的是推论：

**每一批臂都至少有一个是冷的，而且这不是偶发、是结构性的** —— 因为 **后一臂的加载必然挤掉前一臂的模型**，所以无论跑几批，`arm1` 与 `arm2` 永远各自冷启动一次（先载 A 再载 B，B 的加载把 A 挤掉；下一批 A 又得重载）。

**建议把 §3.2 改一下措辞**：你们的"第 3 步（不硬凑、记事实、声明不可比）"**不是 fallback，是计划本身**。具体：

1. 预热降级为「**只预热第一个臂的模型**」——那是唯一还能生效的场景（`arm1` 命中热模型、`arm2` 反正会冷）；
2. **单独测一次两模型的载入耗时**（本机参考值：4b@8192 ≈ **11.4s**、1.7b@8192 ≈ **7.5s**），作为**已知常数**写进报告 —— 读者能把"加载"从 `dur_ms` 里估扣；
3. 报告的速度一节**不做跨臂 `dur_ms` 比较**，`dur_ms` 与 `usage.out` 成对给（或给 tok/s 并声明"含加载 + 含思考 token，两个方向都不纯净"）。

> 若你们想拿"稳态"读数，还有一个办法（但要你们判断是否破坏 2 臂设计）：**加一个同模型重复臂**——`arm2` 与 `arm3` 同模型时，`arm2` 负责把模型载进来（冷）、`arm3` 命中热的（稳态）。这相当于用一臂买一个"热读数"。

## 四、⭐ 实测二：你们的预热方案有一个**会白做**的陷阱（端点不同）

**这是我认为本轮最要紧的一条。** 你们的预热走 native `/api/generate`，而**臂走 `/v1/chat/completions`** —— **两个端点对 `num_ctx` 的处理不同**。实测：

```text
预热：/api/generate  options.num_ctx=2048   → /api/ps 显示 ctx=2048      ✓ 预热生效
随后：/v1/chat/completions（max_tokens=1）  → 耗时 4.3s（！）
      /api/ps 显示 ctx=4096                  → 模型被【重载】了，预热白做
```

**根因**（我们早先单独实测过、这次看到它的连带后果）：**`/v1` 忽略 `num_ctx`**，回落到模型的 Modelfile 值；而 `/api/generate` 尊重 `options.num_ctx`。所以：

- 若你们预热时传了 `options.num_ctx`（且与 Modelfile 不一致）⇒ 预热加载的窗口 ≠ 臂请求解析出的窗口 ⇒ Ollama **在臂请求里重载模型**，那 4.3s 直接落进臂的 `ttft_ms`/`dur_ms`，**预热完全白做、还多花一次加载**。
- **正确做法**：**预热只按派生模型名请求、不要传 `options.num_ctx`**（窗口由 `PARAMETER num_ctx 8192` 带入）——这样预热窗口与臂窗口**必然一致**。

⇒ 你们 §五 checklist 第 [2] 条建议改写成：`预热 = 按派生模型名 POST /api/generate（**不传 options.num_ctx**），带长 keep_alive`。这也是你们走"派生模型"路线的又一重收益，值得在报告里点一句。

## 五、`keep_alive` 格式坑（实测，顺手报一个可能的 400）

我实测三种写法：

```text
keep_alive: "1h"       → HTTP 200   ✓
keep_alive: 3600（数字） → HTTP 200   ✓（数字按【秒】解释）
keep_alive: "3600000"  → HTTP 400   ✗（裸数字串不被接受）
```

你们 §3.2 写"生产用的是 `3600000` = 1h"——**请确认那是数字还是字符串**。若是字符串，会直接 400（我们今天第一次实验就这么撞了）；若是数字，`3600000` 秒 = 约 41 天（无害，但不是你们以为的 1h —— 1h 要写 `3600`）。
