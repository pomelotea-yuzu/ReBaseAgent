## 4. P1 问题

### P1-1 三份文档缺仲裁条款，权威关系不明确

roadmap 首段自称"用户已认可本轮调整方向"，而 usability 与 open-source 首段均自称"讨论稿"。但三份互相引用时是**平级**的：

- usability §4 末："打包基线、版本识别、检查命令和实包验收统一维护在路线 §9.1"
- open-source 首段："竞争验证与实施顺序统一见[隔离重跑路线] §3、§10"

问题：一旦三份在排期上冲突（例如 usability §3 的"第一轮"是否等于 roadmap §3.1 时点表的某一格），没有规则决定以谁为准。**建议**在 roadmap 首段加一句范围声明：本文件为三份中排序与范围的权威；另两份的排期如与本文件 §3、§9.1 冲突，以本文件为准。

### P1-2 "A 不新增 `apps/desktop` 实现"缺可判定判据，且已被实际执行突破

roadmap §3.1 写"R1-A 的'后续不新增 desktop 实现'边界保持不变"；拆分说明 §138 写"A **后续**实施不新增 apps/desktop 修改。**已完成的兼容修正保留**"。

问题有两层：

1. **"实现"一词不可判定**。A 实际已改动两个 `apps/desktop` 文件（`src/main/proxy-recorder.ts` 的 `PLAIN_FORMAT_VERSION` 修正、`test/run-repository.test.ts` 的"未来版本"断言），二者都不算"新增实现"，却确实改了桌面包。后续任务若再遇到同类兼容修正，"是否越界"只能逐次争论。
2. **A 的 tasks.md 仍把 `apps/desktop/test/run-repository.test.ts` 列为必须同步的文件**（"实现期发现"第 4 条），即 A 在事实上**不可能**零 `apps/desktop` 改动。

**建议**把判据改为白名单式：明确"允许修改 `apps/desktop` 中既有的版本/测试断言与常量引用；禁止新增 IPC handler、preload 暴露、渲染层组件与 main 侧流程"。这样每个任务都能机械判定。

### P1-3 K0 缺"新归档能力在实包中可达"的逐项核对清单

roadmap §9.1 的"当前差距"段列举了 09-07 之后归档的成果（Trace-as-Test、模型 A/B、代理父本分叉、provider 参数透传、原生运行创建、缓存记账、LLM 失败详情），但 §9.1 第 5 条的实包验收只要求"验证离线 Monaco 资源、该包目标主流程及错误状态"。

问题：**读者无法据此判断新包是否真的覆盖了这 7 项**。这正是 K0 存在的理由（"先补已完成功能体验包"），却缺一张逐项核对表。

**建议**在 §9.1 第 5 条后补一张表：能力名 / 在 UI 或 IPC 上的入口 / 是否可达 / 不可达时的记录方式。

### P1-4 R2.1 未声明状态保真边界，与 R3 口径不对等

R3 明确要求"权限、可执行位、符号链接和空目录若成为支持该模板的必要条件，先扩展状态契约"（§6 交付边界）。而 R2.1 的验收只写"导出清单、字节及哈希一致，不覆盖源目录，二进制不能伪装成文本补丁"（§5）。R1 的契约也明确"权限、时间戳、链接、空目录和外部服务状态不在快照契约内"（§2）。

问题：用户在 R2.1 导出一个含符号链接或空目录的项目时，**行为未定义**——是静默丢弃、报错，还是保留占位？三处口径未能对齐。

**建议**在 §5 的 R2.1 行补一句：导出状态保真度与 R1 快照契约同边界；越界项必须在导出清单中显式标为"未保留"，不得静默丢弃。

### P1-5 七套编号体系并行，缺对照表

同一份 roadmap 内并行存在：

| 体系 | 含义 | 出现位置 |
|---|---|---|
| R1–R5、R2.1–R2.3 | 能力阶段 | §3、§4–§8 |
| A / B / C | 首期工程拆分 | §2、§3.1、§11 |
| K0–K4 | 打包节点 | §9.1 |
| I0–I3 | 真实接入单元 | §3.2 |
| U / P0–P3 | 可用性主线 | §3.1、usability §4 |
| E0–E3 | 证据门槛 | §10.2 |
| M0–M4 | 传播里程碑 | open-source §6 |

其中 R1 = A+B+C 这层映射只在 §2 出现一次（"首期是 R1，包含现有 A3 的 A、B、C 三个 change"）。文档同时声明"R 编号不再代表严格串行顺序"（§3），但 §3 表格的列名仍是"推荐优先级"与"进入条件"，§11 又给出 1–6 的串行执行顺序。

**建议**在 §3 后补一张编号对照表（体系 / 覆盖对象 / 是否代表顺序 / 权威位置），并把"R = 能力标识，顺序以 §3 主线表与 §11 为准"写成明文。

2. **仓库根目录的游离文档** —— `AniPedia_ReBaseAgent_方案审阅.md`（45,773 bytes，2026-09-10 13:51）位于仓库根目录且未跟踪。它不符合 `docs/README.md` 的命名与分类约定（应带日期前缀并归入 `docs/collab/anipedia/` 或 `docs/reviews/`）。`docs/` 被定位为"唯一过程资产落点"，根目录散落会让该约定失效。

## 7. 值得保留的部分

1. **诚实性**——文档在关键处主动声明边界："本次没有开展外部开发者访谈，需求优先级属于工程与产品判断"（roadmap 首段）、"此文没有完成竞品调查，也不预写胜负"（§10.1）、"未解包证明 exe 内全部功能，也未核查远程下载附件"（§9.1）、"仅完成接口定义不能称为支持某类数据库"（§8 完成判据）。这种自我限制应保持。

2. **不预写胜负的对照纪律**——"没有适用能力的任务明确记为不支持，**不从结果中悄悄删除**"（§10.1）；"缓存、费用和耗时改善使用实测条件与区间，不能将某个示例的收益推广成所有任务的保证"（open-source §2）。

3. **R4 不依赖 Shell 的解耦判断**（§7）——把"修改工具参数并真正重做"与命令执行能力切开，可用多个真实参数错误案例提前验证，是正确的降耦。

4. **打包与发布的分离**——"打包或保存体验包不等于上传 Release"（§9.1 末）；"构建成功、change 归档、打出 exe、通过实包验收和发布是不同状态，记录时分开"（§9.1 首）。这条能避免把测试包误报为已发布。

5. **降级而非删除的处理方式**——模型 A/B 从 R3 前置降为按需，但同时明确"R2.2 最小功能作为该案例的显式依赖"，既解除阻塞又保留交付路径（§3、§5）。
