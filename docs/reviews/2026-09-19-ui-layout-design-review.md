## 1. 审阅发现

### P2-1：IPC 成功与运行正常结束没有分层，会误清失败草稿

位置：设计 §12.1 第 356 行、§12.2 第 375 行，以及 §9.5 第 274 行。

状态流以“收到成功结果”转 Completed，成功后打开新运行，并规定清除该次草稿；但没有定义这里指 IPC 信封成功还是持久运行的终止结果。§3 第 69 行虽正确要求按终止事件判断运行状态，§12 的操作流和 §9.5 的草稿清理没有接入这条规则。

当前证据：

- `packages/agent-loop/src/run-loop.ts:151` 在模型错误时写入 errored 事件，并正常返回结果。
- `packages/replay/src/replay-run.ts:104` 调用 runLoop 后直接在第 112 行返回 ID；`prompt-replay-run.ts:91`、第 99 行同样如此。
- `apps/desktop/src/main/ipc.ts:101`、第 140 行将这类分叉包装为成功信封；普通创建则另行把模型失败转为 CREATE_RUN_FAILED，几个入口语义并不一致。

触发方式：普通 result 或 prompt 分叉遇到模型错误，UI 收到成功信封和新 run ID。若按 §12 的字面流程实现，操作会显示成功并清除草稿，而新运行概览同时显示失败，违反本稿“失败保留草稿”的要求。

建议：拆成请求完成、记录已定位、终止结果已确认三个判断。收到 ID 先读取新运行结果，正常结束、出错、上限结束、已中止和状态未知分别处理；未确认结果时保留草稿。是否自动打开新记录与是否宣布成功、清除草稿分开决定。

补充验收：成功信封但 run reason 为 error、达到上限、结果详情读取失败，以及模型失败信封但失败记录已落盘。覆盖 result fork、prompt fork 和原生创建的差异。

### P2-2：结果未知状态没有恢复或释放执行槽的规则

位置：设计 §12.1 第 358 行、§12.2 第 369 行及第 380 行、§16 第 495 行。

设计引入 Unknown 状态，但只提供刷新记录；同时规定全局只有一个在途操作槽，执行期间禁止新提交和配置修改。没有说明 Unknown 是否继续占槽、何时可以解除配置锁、用户退出操作面板后的状态以及迟到结果如何归属。

当前能力表又明确请求完成前没有 run ID，也没有任务状态查询或恢复通道，因此刷新列表未必能可靠匹配本次操作，不能把“列表刷新成功”视为执行已经结束。

触发方式：执行结果在通信故障后未被确认。若继续占槽，用户可能无法再执行或修正配置；若直接释放并允许重试，旧请求可能仍在运行，不能再承诺只有一个执行且无重复副作用。

建议：明确 Unknown 的转移条件和可用操作。能关联到确定终止记录时收口；无法关联时保留未知标记，不能宣称已终止。当前能力下写清需要重新建立会话等可行恢复边界；若要求原会话内可靠恢复，就把操作关联 ID、任务状态查询与主进程执行门禁列为基础依赖，而非笼统后置增强。

补充验收：结果未知后关闭/重开面板、刷新无匹配记录、迟到结果、尝试新执行及修改设置；每条路径都有确定状态，且不自动重发。

### P2-3：缺父链时继续阅读的承诺缺少降级读取契约

位置：设计 §18.2 第 567 行、§19 第 607 行，与 §20.2 第 649 行的 main/shared/preload 分工。

设计要求父链缺失时仍可阅读已有内容并比较可得信息，但当前详情接口不是对所有分叉类型都能返回部分结果：代理和 prompt 分叉有溯源链降级，普通工具结果分叉则依赖完整 resolveBranch。

证据：`apps/desktop/src/main/run-repository.ts:84` 对普通分叉直接调用 resolveBranch；`packages/trace-sdk/src/branch.ts:48` 在父记录缺失时抛出错误，导致整个详情请求失败。渲染层拿不到该子运行的自有 spans，无法仅凭布局改造完成降级。

触发方式：保留子运行 JSONL，移走其父运行，再打开子运行。按当前接口只能看到详情失败，达不到设计的“仍可读已有内容”验收。

建议：在 U 中明确增加只读降级详情契约：经完整校验的叶子自有记录、可得来源及结构化的父链不完整原因。降级不能伪造共享前缀，执行仍由严格预检拒绝；也不能把 schema/版本校验错误一概吞掉。如果暂不扩展接口，就将该路径定义为详情不可用，而不是承诺完整的部分阅读体验。

补充验收：普通 result 分支、隔离 result 分支、prompt 分支、代理分支分别覆盖父记录缺失；另测父记录损坏、未来格式和正常父链，防止降级掩盖格式错误。

### P2-4：简化列表时移除了辨认模型实验臂的关键信息

位置：设计 §7.1 第 183–185 行，关联 §15.4 的模型实验流程。

三行列表只包含任务摘要、状态/时间和分支来源/修改类型，没有要求显示模型或稳定的运行标识。已有 `RunSummary.model` 可直接使用，当前 `RunList.tsx:133` 也会显示模型。

触发方式：同一任务发起两臂 A/B，两个运行 task、状态、修改类型相同，创建时间也可能落在同一显示精度内。列表会出现难以辨认的重复条目，开发者必须逐条进入概览或分支树才能确认模型，与列表“区分多次尝试”的目标相反。

建议：第二行保留模型与状态，时间降低权重；实验记录显示稳定臂标识，或在同任务记录之间提供短 ID 作为区分。不同参数但同模型的臂也要可辨认，不只补一个模型名就结束。

补充验收：同任务不同模型、同任务同模型不同参数、同一显示时间、重复 result 分叉及长模型名，在窄侧栏中均能辨认。

## 2. 初审结论与限制

本轮未发现需要推翻整体信息架构的 P1 问题；发现 4 项 P2，应在拆分实施任务前修订，其中前两项直接影响完成反馈和草稿保存。

概览优先、运行导航与内容分层、文件只读、B/C 的执行边界可以保留。当前文档作为 V0.1 设计草案成立，但不能视为已完成可执行的全部状态契约。

另外，创建工作区替代列表标题对话框、完成后不强制抢焦点等改动，会改变既有 desktop-ui/B 的明确行为要求。本稿已要求受影响 spec 更新，因此本轮不作为未识别缺陷另列；实施拆分时必须落实到具体 requirement，不能只更新 tasks。

初审为静态审阅，没有运行模型请求或桌面测试；布局密度、断点、键盘路径和真实用户上手情况仍需原型及实机验证。初审时设计正文与应用代码均未修改；后续正文修订记录如下。
