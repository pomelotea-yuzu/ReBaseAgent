## 2. 为什么要拆（三句）

1. 61 小时放在一个 change 里，主 spec 要到较晚才第一次更新；拆开后分段验收、归档。存在依赖的后续阶段不能在回退前置能力后继续使用。
2. design 自己的 Migration Plan 写的就是这个顺序：「先双读、再存储、后桌面入口；**未完成拒绝门禁前不开放隔离创建**」——阶段划分本身就是拆分线。
3. 一次审 6 份 delta 的审阅成本较高；拆开后 A 有 5 份，B/C 各 1 份，后续评审建立在已归档的契约上。拆分减少单次范围，不会自动减少实现总量。

## 7. 硬约束（写进三个 change 的 design，勿违反）

1. **A 不包含 desktop-ui delta，也不在其他 delta 中承诺界面行为**。归档 A 时包层数据、错误与执行契约必须全部可验收。
2. **A 的 apps/desktop 修改仅限版本兼容白名单**：因共享包版本兼容而必需的既有版本/测试断言与常量引用修正，保留既有行为及拒绝门禁，并记录原因和回归证据。已完成的兼容修正保留，不重复列为待办；禁止新增或扩展 IPC handler、preload/store 暴露、渲染层组件和 main 侧流程，隔离桌面工作归 B/C，可用性工作归独立 U 变更。白名单外先调整受影响分工及 OpenSpec。A 的专项验收直接驱动 packages API；公共全仓回归和桌面构建仍须运行，不等于将桌面功能划入 A。
3. **A 交付 createIsolatedRun/replayIsolatedRun 及明确的 dataDir 参数契约**。创建/分叉和文件读取所需的纯数据、附件读取/校验接口在 A 完成；B/C 只加集成和呈现。A 的包门禁必须在隔离 API 开放前完成；B 的 IPC 校验与桌面门禁必须在桌面创建入口开放前完成。
4. **trace-format 和 workspace-isolation 的新增契约在 A 收口**。按 §5 迁出 IPC/显示义务后，B/C 仅消费。若实施发现契约缺口，暂停依赖项、修订计划及受影响 spec；A 已归档时通过明确的新变更处理，不能静默改已归档事实。
5. **A 负责配额、profile、迭代/用量预算与每次请求授权**；B 不重定义规则，C 不取得执行能力。历史审计字段不授权新请求。
6. **MODIFIED 是整体替换**。完整保留主 spec 已有场景；本 A3 新增或扩展的跨阶段义务按 §5 拆开，并在目标段建立场景和任务引用。保留标题不等于可以继续要求未交付功能。
7. **B/C 顺序交付**。B 不依赖 C 的文件页或只读文件 IPC；C 复用 B 的详情 IPC 与来源信息，新增自己的文件读取契约和校验。
