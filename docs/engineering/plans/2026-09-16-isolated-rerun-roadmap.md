## 1. 产品目标与优先级ReBaseAgent v0.3.0-k0-a3.1 预览版

让开发者能完成一条连续流程：

**找到 Agent 出错的步骤 → 修改输入或操作 → 在独立状态中执行 → 用文件差异或测试判断结果 → 将有用结果带回项目。**

主攻维护多步文件或代码 Agent 的开发者。目标是在他们已有项目中缩短“定位错误到验证修复”的过程，提供可带回项目的结果。先支持一种明确技术栈，再按重复需求扩展；数据库、远程 API 等状态适配后置。

**竞争目标是“接得进、修得动、验得出、拿得走”。** 验收以真实任务完成情况和相对原有方法的效率为依据，不能以功能条目、一次演示或 Star 数替代。项目继续保持免费开源，增长材料来自有记录的实际案例，不预设已经优于任何竞品。

**近期安排：以已归档的 R1 和已打出的 A3 预览包为基线，推进可用性 U、K1 体验包及真实项目接入验证 I。** U 先修已有界面，I 先验证技术栈与实际工具契约，同时补齐预览包尚未完成的实机验收。排期同阶段不要求同时修改相同模块；按独立单元顺序集成。后续先交付结果导出和单环境测试，完整模型 A/B 不再是它们的前置。

| 开发者的问题 | 产品需要回答什么 | 路线落点 |
|---|---|---|
| 不知道在哪一步跑错 | 当时输入、工具结果、文件状态、错误及后续变化 | R1 与可用性改进 |
| 改了以后不知道有没有用 | 修改位置、最终输出、文件差异和执行消耗；代码任务有真实测试证据 | U、R2.1 与 R3 |
| 实验成功，却无法使用产物 | 完整文件导出、文本补丁和可核对的来源 | R2.1 |
| 代码看起来正确，但不知道能否运行 | 同一环境中的测试、退出码、日志与产物 | R3 |
| 写错路径或命令，想重做那次操作 | 操作前检查点、参数修改、真实工具重执行 | R4 |
| 我的工具接不进来 | 先接通一种技术栈及实际文件工具，后扩展其他状态 | I 近期主线，外部状态归 R5 |

当前普通重跑在分叉点之后已经可以真实执行工具；A3 新增的是历史文件状态和分支隔离。不能把旧文档中的“所有工具都只喂录制结果”当作当前普通重跑实现。

首期明确限定：

- 固定 `read_file` / `write_file` 工具，操作应用管理的文件映射与不可变内容附件。
- 记录初始状态和每轮全部工具结束后的检查点；编辑工具结果后，从该轮末尾的状态继续下一轮模型调用。
- 编辑结果只改变模型观察到的文本，不撤销原工具写入，也不重执行被选中的工具。
- 普通文件字节可恢复；权限、时间戳、链接、空目录和外部服务状态不在快照契约内。
- 不执行 Shell、自定义 handler 或整个项目构建；隔离父本的 prompt fork 和模型 A/B 首期拒绝。
- 旧 trace 没有录下的文件状态无法事后恢复。代理录制能提供模型请求与响应，但不能据此重建外部工具实现或历史工作区。
- 模型仍会真实请求用户配置的服务商，存在费用和输出不确定性；文件隔离不代表网络离线。

现有首期约束以 OpenSpec 为准。本路线的后续内容不能被当作放宽首期执行门禁的依据。

### 3.2 I：先接通一种真实技术栈

先以 **Node/TypeScript、OpenAI 兼容模型协议、模型驱动文件工具调用** 的现有 Agent 为候选，复用当前代码优势。这是技术验证起点，不是已证明的市场覆盖结论；具体框架及版本在首批真实项目中选择，只支持一个明确组合。

| 单元 | 现在要准备什么 | 通过条件 |
|---|---|---|
| I0 选定对象 | 一个仍在维护的 Agent 项目、具体框架/版本、工具表、执行入口及失败任务 | 任务由项目使用者判断正确与否；能说明原来如何排查，不为演示重造一个替代 Agent |
| I1 接入与状态验证 | 最小埋点或适配示例，记录模型消息、工具参数/结果及文件状态；列出缺失契约 | 原 Agent 主体仍运行；记录接入耗时、改动文件和维护者帮助；仅录到 trace 不算完整接入 |
| I2 支持实际重跑 | 明确原工具在隔离状态中的实现/映射、恢复边界及执行版本，形成独立适配提案 | 至少一次原项目真实失败能在受支持工具范围内重跑，保留原目录，产物有判据；工具桩不能冒充真实执行 |
| I3 自助复现 | 把该组合的接入步骤、示例和错误诊断交给另一位开发者 | 对方能按文档完成支持路径；记录是否需要代改代码，未通过时先修接入而非扩大框架数 |

最小目标是不要求开发者迁移整个 Agent 引擎。必须显式记录适配是否改变工具行为；更换宿主引擎或把原工具改写成专用演示工具，只能算迁移试验，不能作为低成本接入通过证据。

I0/I1 可与 R1 实施同期开展，I2 消费已验收的隔离能力。R1 固定工具组不接收任意 handler 的约束保持不变；框架桥接、工具版本映射和执行授权由新的 change 定义并验收。原运行缺少文件快照时，只能从接入后新采集的运行开始，不能修造历史状态。

先对第一个项目写具体适配，再由第二个真实项目的重复部分决定公共接口。若首个候选只能靠大规模重写才能运行，记录成本并调整候选，不立即建设通用插件平台。I 和外部状态扩展 R5 分开验收。

## 4. R1：交付可用的隔离文件重跑

### 代表任务

Agent 根据一份配置生成输出文件。开发者发现某步读取结果有误，修改该结果后继续执行，查看新分支文件，同时保留原目录与父分支。

### 交付

按 A3 已有拆分依次完成内核、桌面操作和文件查看。执行范围确认、错误反馈、返回原运行、窄窗口可读性纳入相应桌面验收，与可用性规划共用交互设计。

### 完成判据

- 包集成案例证明：父运行先写 `middle`、后写 `after`，从前一轮分叉后首次读取为 `middle`；子运行写 `child` 后源目录、父与兄弟内容哈希不变。
- 首期完整流程可以在桌面完成，用户能辨认选中的父运行、轮次、修改位置和新分支。
- 重启后可以查看轨迹、检查点及差异；缺失和损坏附件明确报告，不能从现有源目录补造历史。
- 前缀模型与工具调用数为零，只执行续跑部分；多工具同轮和二次分叉均有证据。
- 各段按既有任务完成公共检查、桌面构建和专项验收。产品演示必须使用包含该能力的实际构建，归档代码不等于已发布安装包。

## 5. R2：先带出结果，实验按需扩展

### 为什么紧接首期

开发者验证了修复后，需要把产物带回原项目。R2.1 结果导出紧接 R1；prompt 和模型比较虽然也能复用快照，但不能阻塞真实任务接入与测试执行。R2 不再作为一个整体进入 R3 的门槛。

### 分开交付的三个单元

| 单元 | 范围 | 优先级与验收重点 |
|---|---|---|
| R2.1 结果带出 | 导出选定检查点到新的空目录；提供相对明确基线的文本补丁 | 首先交付；导出清单、字节及哈希一致，不覆盖源目录，二进制不能伪装成文本补丁；状态保真度与 R1 快照契约同边界，越界状态在导出清单中显式标为“未保留”，不得静默丢弃 |
| R2.2 隔离 prompt 实验 | 修改启动 prompt，使用同一份初始文件快照从头执行 | 真实修复案例需要时做最小单分支；新分支独立，上下文与文件起点一致，显示真实费用边界 |
| R2.3 隔离模型 A/B | 同一输入与初始快照，顺序执行不同模型或参数的实验臂 | 完整多臂扩展后置，原则上在 R3 首个真实任务通过后；各臂状态独立，输出和消耗可比较 |

结果带出优先于自动合并。后续若需要直接应用到原项目，另立变更，要求核对基线哈希、显示冲突和明确的应用操作；不将“导出成功”当作“合并成功”。

导出清单须列明权限、可执行位、时间戳、链接关系、空目录及外部服务状态不在 R1 保真范围。快照未记录的项目标为“未保留（原状态未知）”，不能回读当前源目录猜测历史逐项状态；有记录的越界项逐项说明。R1 导入拒绝的符号链接不能借导出转为支持，硬链接只按独立文件字节导出。若目标项目依赖这些状态才能使用，记录为该项目尚不受支持；先扩展状态契约并同步导出验收，再宣称完整恢复，与 §6 的 R3 要求一致。

### 实验语义

- 第一版隔离 prompt/A-B 固定从明确的实验基线初始快照开始，不能使用父运行最终文件配合原始启动消息。
- 若父本本身是中途续跑分支，不能默认为独立完整实验。建议首版拒绝这种实验起点，并提供回到对应根基线的入口；支持任意中间实验起点须另行定义消息与文件配对契约。
- 工具实现和执行环境保持一致，每次改变的因素明确记录；模型或 provider 版本无法固定时如实记录限制。
- 耗时、token、缓存按同一口径显示，缺失费用数据标为未知。单次生成有波动，不能自动据一次实验判定模型优劣。
- 文本结果由用户判断，结构化产物可按项目提供的确定性规则核对。首版不引入通用自动评分器。

### 代表性验收

R2.1 使用 R1 已产生的修复分支验证导出：用户能指出修改、文件差异与消耗，将选定结果导出到新目录，内容与选定检查点一致，源目录和父分支不变。这个验收无需两个 prompt 或任何模型 A/B 功能。

R2.2/R2.3 实际交付时再验证同一初始快照下的 prompt 或模型实验，各自新增场景不追溯成为 R2.1 的交付条件。

若案例确实需要发现文件，新增受控列目录或搜索工具作为独立小变更，给工具组新版本并校验兼容性。删除、重命名等按用例引入，不修改 `file-tools-v1` 的既有含义。

## 6. R3：运行测试和构建

### 代表任务

Agent 在小型 TypeScript 项目中修改一个函数，运行项目已有测试。开发者比较失败分支与成功分支的代码、测试输出和退出码，再导出修改结果。

这是首期和导出之后的下一项核心能力。技术验证可以在 R1 后期独立准备，无需等完整模型 A/B：开发者需要能检查的执行证据，文件差异本身无法证明代码正确。通过测试仅证明所运行用例的结果，不等于完整正确性。

### 先做技术验证，再开放命令执行

R1 的文件映射不能直接作为进程工作目录。R3 必须新增独立的项目物化、进程执行和产物回收能力，不能只把现有 Shell 的 `cwd` 指向一个临时目录。

先选择一个维护中的隔离执行方案进行 Windows 验证。候选包括容器或基于虚拟化的执行环境，具体选择取决于本机可用性、安装要求、文件与网络限制，以及取消后能否收掉子进程。Linux 容器执行与 Windows 原生执行必须分别标明，不能声称环境等价。

技术验证没有通过时，该能力保持未开放；不会自动退回宿主 Shell 执行。高级执行后端可以是可选依赖，R1/R2 保持原有便携使用方式。

### 交付边界

- 首个受支持环境限定一个明确的 Node/TypeScript 模板、锁定依赖与固定测试命令，不从第一版支持所有语言和构建系统。
- 记录项目初始内容、运行时或镜像版本、锁文件、命令、参数、工作目录和受控环境配置；凭据不写入 trace。
- 依赖准备与正式实验分开，记录准备结果。实验阶段固定依赖，网络策略明确；安装脚本也是代码执行，必须在同一隔离边界内。
- 宿主目录、环境凭据、网络、进程、时间及输出容量均有实际限制；工具名称或 `sideEffect` 标志不能替代隔离机制。
- 每条命令记录 stdout/stderr、退出码、耗时和产物变化。超时、取消、崩溃和正常失败分别呈现；取消要覆盖子进程并阻止后台继续写入。
- 执行结束、全部相关进程停止后才采集文件检查点，校验链接、路径、配额与稳定性。构建缓存、依赖目录和临时文件的排除规则须显式记录。
- 权限、可执行位、符号链接和空目录若成为支持该模板的必要条件，先扩展状态契约；不能沿用 R1 字节保真度却宣称完整项目环境可恢复。

### 完成判据

同一初始状态下得到一次已知测试失败和一次修复后通过，二者日志与产物可核对。另用越界访问、网络请求、超时与子进程案例验证所承诺边界。源目录和兄弟分支不变；取消和重启后无遗留执行。

首个案例计划以届时已验收的结果编辑和隔离续跑为基础，串起“修改工具结果 → 隔离续跑生成代码 → 在同一环境跑测试 → 导出结果”，不依赖 R2.2/R2.3 或 R4。若项目错误只能通过修改 prompt 修复，明确增加 R2.2 最小单分支作为该案例依赖，并从共同初始快照从头执行；不把人工改了文件却未记录干预的过程说成 Agent 自己修复。

固定小项目 fixture 用于工程验收；对外主张修复效率前，还须在 I 接入的真实项目完成同类任务与 §10 对照。仅在专门制作的模板上成功，不代表已经支持用户已有项目。

## 7. R4：修改工具操作并真正重做

### 代表任务

Agent 将文件写到了错误路径。开发者修改 `write_file` 的路径参数，回到这次写入之前执行新操作，再让模型继续。与 R1 修改返回文本的操作明确区分。

### 必须先补的契约

- 新运行记录工具调用前后的检查点、实际执行顺序、工具版本和输入。旧 R1 轨迹只有轮末快照，不自动获得更细恢复能力。
- 首版建议限定固定文件工具且串行执行。选中调用之前的同轮工具结果和文件状态保留；被选中及其后的同轮工具重新执行，旧的后续结果不再复用。
- 改参数属于一次显式人工干预：父录制保持原样，子分支记录原参数与修改值；发给后续模型的 assistant 工具调用参数、调用 ID 和新工具结果必须一致，不能让上下文仍声称执行了旧操作。
- 工具定义、代码或输入文件有变化时，区分“同条件续跑”与“变更后的实验”，不绕过既有配置一致性门禁。
- 并行工具若没有可证明的顺序与一致检查点，暂不支持其中单个调用回退；未来可定义整个并行批次重新执行。
- UI 分别呈现“修改返回结果后继续”和“修改参数并重新执行”，显示恢复点、真实执行范围及当前授权。

### 完成判据

新写入落在修改后的路径，旧的错误写入在新分支恢复起点不存在；前置工具未重做，后续消息与文件事实一致。父分支保留原错误写入，兄弟分支不变。同轮多工具的重复执行范围、失败和取消都有可核对记录。

该阶段可能需要新的 trace 能力或格式版本，须单独评审兼容策略；不得静默扩大现有 `result` 编辑语义。

## 8. R5：扩展更多工具与外部服务

### 先解决接入，再扩大状态范围

首种真实技术栈接入已经前移到 §3.2 的 I 主线，本节仅承担后续更多工具、框架与外部状态扩展。SDK 或代理能记录调用，并不意味着 ReBaseAgent 能接管执行引擎。每个新增适配仍需声明工具版本、状态来源、执行入口及支持的重跑模式；缺任一项时保留只读查看能力并说明限制。

先用第二个真实项目验证 I 的接口是否可以复用，再扩展能力。已有 AniPedia 可继续验证模型实验，但它没有模型驱动工具调用的路径不能充当文件重跑验收；只读代码问答项目可验证文件检索适配，写入和命令执行仍须满足对应阶段边界。

| 工具或状态类型 | 建议接入方式 | 不能自动推导的保证 |
|---|---|---|
| 纯计算 | 固定实现版本与参数后重执行 | 名为“只读”不代表确定性 |
| 文件检索、代码搜索 | 针对选定不可变文件快照执行 | 查当前宿主目录不等于查历史文件 |
| HTTP 读取 | 显式选择录制响应或实时请求 | 实时服务内容不会自动回到历史 |
| 数据库、RAG、记忆 | 独立测试实例、数据快照或版本化数据集 | 文件快照不能恢复任意远程状态 |
| 发消息、付款、业务写 API | 默认阻断真实外发，使用测试端点或模拟实现 | 幂等键和补偿不等于能撤销全部历史副作用 |

每个适配必须声明状态归属、恢复方法、失败处理、授权及哪些结果来自录制。不同执行模式可组合，但界面和 trace 必须可辨认；不将录制返回值显示为刚刚真实执行的结果。

### 完成判据

对每个支持的适配，交付最小接入示例、固定测试数据、一个真实失败修复案例及状态不变性证据。仅完成接口定义不能称为支持某类数据库或所有 Agent 框架。

## 9. 跨阶段持续工作

### 示例与试用

可用性按 §3.1 作为独立主线推进。执行能力按运行来源和数据完整性派生，不能对所有 trace 展示同样的重跑承诺。

每阶段保留一份公开案例，提供可离线浏览的已录制结果；真正新建模型分支时才使用用户配置。演示及发行材料与实际可下载版本一致。

### 数据寿命与容量

R1 已有单次配额，尚不解决运行长期积累的磁盘占用。R2 阶段开始观察真实增长，增加占用说明和包含附件的备份指引。

共享附件清理单独立项：先确定所有保留运行、父链和快照的引用关系，再处理未引用内容；明确并发写入、临时文件和中断恢复。当前旧运行删除能力不能直接升级成删除共享 blob。磁盘增长形成实际使用阻碍时可提前于 R3，不因它不是主功能而无限推迟。

### 回归验证

保留三个不同层次的验证：现有 Trace-as-Test 验证运行时对录制响应的处理；文件隔离测试验证状态与分支不变；R3 项目测试验证特定产物行为。

卡带测试不会自动发现 prompt 或模型质量回归。未来接 CI 时分别提供明确入口、环境前提和费用行为，不能复用一个“回放成功”表示三者全部通过。

### 技术与发行

继续复用现有包边界和 JSONL 事实源。新增格式先定义旧数据行为，新增工具组或执行后端明确版本；按阶段运行相关测试、完整质量检查和桌面构建。

Windows 是首个验收平台。跨平台发行独立评估，不能从“底层库跨平台”推导“隔离后端和桌面都已支持”。

|---|---|---|

R1-A 单独完成只有包层能力，通常不为它专门做用户体验包；涉及打包依赖、资源加载或便携数据路径时，应增加技术验证包。纯文档、测试或内部重构无需例行打包。

K3 可以按首期已实现范围正常发行；用于宣称竞争优势的后续 K4 修复验证包，必须再附 §10 的真实任务和对照证据。单纯打出包不能作为对比成功依据，收集证据也不阻止日常体验包发给维护者使用。

建议开发活跃期每周核对一次“源码已完成但最近体验包尚未覆盖”的用户可见变化。有完整且已验收的变化就安排体验包；只有未完成能力时继续开发。这个周期是工作约定，不是定时自动打包或发布任务。

#### 每次打包的最小完成条件

1. 确定基线与范围：记录提交、工作区差异、包版本和目标能力。当前桌面与根包版本为 `0.3.0-k0-a3.1`（A3 阶段预览版），builder 用版本生成文件名；下一包的版本按目标调整（新体验包继续使用可辨认的预发布标识，或独立构建标识与输出目录），保留旧 exe 及原 `data/`，不覆盖成同名“新旧混合包”。正式发行使用新的明确版本，具体编号在发行准备时确定。
2. 准备发行检查：**版本与产物名已改为同源推导**（`allow-versioned-release-identity`，09-17 归档）—— `apps/desktop/scripts/release-check.mjs` 从 `apps/desktop/package.json` 的 `version` 推导期望产物名（`expectedArtifactName(version)`），`apps/desktop/scripts/release-verify.mjs` 明确“不硬编码版本”，`apps/desktop/test/release-check.test.ts` 里只剩夹具字面量（并已覆盖 `0.3.0-k0` 这类带后缀版本）。⇒ **打新版本时不需要再手改版本断言**；只需确认目标 `version` 与体积边界 `BYTE_LIMIT = 100,000,000`（单文件严格小于）未被放宽，资源校验未被绕过。（原 09-17 记录的行号与 `EXPECTED_APP_VERSION` / `EXPECTED_ARTIFACT_NAME` 常量已不存在，此条按当前实现重写。）
3. 在选定基线上运行 `pnpm check:ci`，先构建共享包再运行测试；运行 `pnpm --filter @rebaseagent/desktop build` 验证完整桌面资源。正式发行随后执行 `pnpm --filter @rebaseagent/desktop dist`；体验包执行 `pnpm --filter @rebaseagent/desktop dist -c.directories.output=../../release/preview`，显式覆盖默认的 `release/stable/`。该脚本构建桌面并调用 builder，但不替代共享包构建和前面的检查。
4. 对本次新产物运行适配目标版本后的 `release:verify`，使用其真实路径，记录 SHA-256、字节数与结果；沿用单文件严格小于 `100,000,000` bytes 的当前发行要求。Gitee 已于 2026-09-23 确认为面向大陆用户的主要分发渠道，继续沿用既有体积预算；这不是 GitHub 附件上限。R3 评估可选执行后端时分别记录便携包、后端下载和运行环境占用，后端不默认塞入便携 exe；需要调整渠道或预算时另行修订发行要求。源码/构建资源检查不能单独证明打入 exe 的资源完整，仍须下一项实际启动验收。
5. 在独立测试目录双击该便携 exe，使用全新数据目录验证首次启动，再用历史数据的副本验证读取、重启、设置持久化和数据落点；验证离线 Monaco 资源、该包目标主流程及错误状态。涉及新文件格式时增加版本兼容和附件恢复用例。历史数据只使用副本，不用唯一原件做升级试验。
6. 留下简短构建记录：版本/提交、文件与哈希、验收结果、包含功能、已知限制和回退方法。发布材料不携带本机 `release/data/`、API 凭据或私人 trace。正式介绍和录屏在实包验收后进行；有真实 provider 冒烟时记录费用和结果，使用模拟服务时明确验证边界。

## 10. 真实任务、对照与竞争验证

首轮安排 3 至 5 名正在维护文件工具或代码 Agent 的开发者，使用其真实项目和能判断正确与否的失败任务。先记录原来怎么排查，再提供接入帮助。参与者可与可用性和增长规划共用，不重复组织多套活动；本次未发送邀请。人数是发现问题的规模，不是市场统计结论；只有内部案例时明确记录。

| 观察项 | 记录内容 | 如何影响排序 |
|---|---|---|
| 接入 | 从原 Agent 到首个可重跑任务的耗时、改动文件、工具适配和维护者帮助 | I 当前优先解决，不能只按首个 trace 已出现判定成功 |
| 调试流程 | 找到问题、完成修改、看懂差异所需提示 | 基础流程仍需反复指导时，先修 R1/R2 体验 |
| 修复证据 | 文件规则、实际测试和导出产物是否足以判断修复 | R3 首个受支持环境优先于完整隔离模型 A/B；不先扩展框架数量 |
| 操作粒度 | 错误来自 prompt、工具结果还是具体参数 | 多个真实案例都卡在操作前恢复时，提前 R4 |
| 结果使用 | 是否成功导出、是否仍需大量手工搬运 | 决定补丁或显式合并需求 |
| 重复使用 | 后续是否再次用来调试，卡在哪里 | 判断下一阶段是否解决日常问题 |

文件是否改变用哈希核验，测试结果用实际退出码和日志核验；模型表现按任务记录，不能以一次成功作为普遍保证。没有直接相关的试用证据时，不以追求完整功能清单为理由扩展外部状态范围。

### 10.1 同任务公平对照

先建立至少 5 个失败任务的初始记录，覆盖错误工具结果、错误文件内容、调用失败、多个工具步骤和修复后测试失败等实际遇到的类型。至少部分任务来自外部项目；拿不到时将对照标为内部工程验证，不能宣称用户竞争优势。没有适用能力的任务明确记为不支持，不从结果中悄悄删除。

对照对象包括 **开发者现有的“日志 + 手工重跑”方法**，以及 1 至 2 个用户实际考虑使用的竞品。执行前核查具体产品、版本/日期、套餐、平台、接入方式和相关功能，采用其合理配置；此文没有完成竞品调查，也不预写胜负。

| 指标 | 记录口径 |
|---|---|
| 接入成本 | 首次安装配置到首个可调试任务的总用时、代码改动及人工支持；与后续单次修复耗时分列 |
| 验证修复耗时 | 从看到失败到得到事先规定的通过证据，包含定位、修改、等待、重复尝试和导出；注明人为干预 |
| 模型消耗 | 真实请求次数、输入/输出 tokens、缓存与可核实金额；价格不全时不编造金额 |
| 完成情况 | 成功、失败、不支持、超时分别记录；工具错误、二次分叉、重启和缺附件的行为单列 |
| 使用门槛 | 误点、需要提示次数、维护者代操作；计时不能扣掉另一方必须进行的手工步骤 |

相同任务使用同一初始文件、可比模型/参数、预先确定的正确性判据和预算。缓存、依赖准备、模型版本及机器环境分别记录；无法一致时列为限制。计时测试使用重复运行或等难度变体，并交替操作顺序，减少“第二次已经知道答案”的影响；保留全部尝试、原始记录和失败，报告样本数与范围，不只挑最好一次。

交替顺序不能消除学习效应。若参与者仅维护者本人，内部对照只报告完成/未完成（并保留失败、不支持、超时原因），耗时可以作为排障记录，但不列为效率或竞争优势证据。E2 的真实执行和导出证据可分别记录，外部效率对照仍标为待验证；可用性和传播材料沿用此限制。

### 10.2 阶段性证据与调整门槛

| 节点 | 最小证据 | 不满足时的动作 |
|---|---|---|
| E0 选题与基线 | 一种技术栈、一个真实项目、原有排查过程、任务判据及待核查竞品清单 | 先补实际对象，不把框架覆盖率作为开发目标 |
| E1 接入与文件修复 | I2 真实重跑、U 主流程、R1 状态不变性；R2.1 完成后能带走修复产物 | 优先修适配和操作阻碍，暂缓完整模型 A/B |
| E2 测试与效率 | R3 真实失败/通过记录、导出产物及同任务对照，明确改善和未改善的情况 | 未更快时分析接入、交互或执行耗时，不用更大功能清单掩盖结果 |
| E3 再次使用 | 首批外部使用者能够自行完成支持流程，并记录是否有人在后续独立问题中主动使用 | 建议在首次使用后 7 至 14 天收集一次自愿反馈；无后续问题记为未知，不能当作留存失败 |

这些是早期产品决策信号，不构成统计性“击败竞品”结论。只有某类任务在正确性和适用范围成立的前提下反复出现明确效率收益，才围绕该场景表达竞争优势。自动化提醒、对外邀请和收集反馈的实际执行另行安排，本次不创建。
