## 1. 背景与问题

当前已经具备运行创建、轨迹查看、上下文预算地图、修改重跑、分支树、模型 A/B 和 Trace-as-Test 等能力。用户在实际使用中反馈：功能入口需要寻找，操作是否成功不够明确，结果也不容易理解和比较。

本轮所说的“更加可视化”，重点是界面的布局、信息层级和交互衔接。图表用于帮助阅读和判断，是否增加某种图表取决于它能否解决具体问题。

当前实现与规划依据：

| 依据 | 与本轮相关的现状 |
|---|---|
| `apps/desktop/src/renderer/src/components/SpanTree.tsx` | 轨迹主要以可展开的步骤树呈现，包含耗时与 token 信息 |
| `apps/desktop/src/renderer/src/components/ComparePanel.tsx` | 对照主要围绕共同祖先、运行指标与累计增量，采用较窄的侧栏 |
| `README.md` | 已有分支树、预算地图、缓存展示和多种运行入口，可在现有能力上改进体验 |
| `HANDOFF.md` | 记录了失败原因未完整落入 trace 的缺口，后续需在源码中核实并补齐 |

本规划中的进度展示、取消、错误详情等均为目标能力。各执行路径的现有支持程度需要在实施前核查。

## 2. 三个改进方向

### 方向一：界面与上手体验

**用户问题：不知道去哪找，也不清楚下一步能做什么。**

建议按使用顺序组织界面：

| 区域 | 主要职责 | 设计重点 |
|---|---|---|
| 顶部全局区 | 新建运行、录制状态、设置 | 入口位置稳定，区分全局操作与当前运行操作 |
| 左侧运行导航 | 查找和切换运行 | 任务名称优先，提供搜索和必要筛选，技术 ID 降低视觉权重 |
| 中央阅读区 | 查看结果、执行步骤与上下文 | 为主要内容提供足够宽度，明确当前选中步骤 |
| 内容操作区 | 编辑、从此处重跑 | 操作靠近对应内容；不满足条件时说明原因 |
| 专门的对比视图 | 阅读两个运行的差异 | 支持宽幅并排阅读，返回后保留此前位置 |

实施原则：

- 默认突出任务、状态、结果和关键步骤；原始 JSON、配置指纹等详细信息按需展开。
- 运行详情、分支关系和实验对比具有明确入口，避免所有视图长期并排挤占空间。
- 统一使用“运行、步骤、修改后重跑、对比”等名称，技术字段保留在详情中供排查。
- 图标配合明确的标签或提示；执行重要操作时，让用户能确认操作对象和范围。
- 空状态提供可以直接执行的入口；已有数据时保留选择、滚动位置和返回路径。
- 窄窗口下通过折叠导航、切换视图保持可读性，避免主内容被固定侧栏挤压。

### 方向二：执行反馈与错误处理

**用户问题：不知道是否还在运行、是否成功，以及失败后该怎么办。**

建议覆盖完整的操作状态：

| 时点 | 应呈现的信息与行为 |
|---|---|
| 提交前 | 本次修改内容、重跑起点、执行范围、工具执行方式；费用提示沿用真实计费语义 |
| 提交后 | 立即反馈已提交，防止重复触发，保留当前操作对象 |
| 执行中 | 显示可靠的当前阶段和已等待时间；能获取步骤事件时再显示具体步骤 |
| 取消时 | 支持的路径提供取消，并区分取消请求已发送与执行已终止 |
| 完成后 | 明确呈现新运行和结果，提供与原运行对比的入口 |
| 失败后 | 展示失败原因、可定位的步骤及针对性的处理建议，保留可用的运行记录 |

实施约束：

- 无法预估完成时间时使用阶段和耗时，不生成虚假的完成百分比。
- 失败原因需要从执行层传递并按需记录到 trace，不能只停留在临时提示中；敏感凭据不得写入错误详情。
- 历史记录缺少错误原因时明确显示“未记录”，不能补造原因。
- 取消能力需核查执行层、IPC、工具调用和落盘行为；取消请求不代表外部工具副作用已经撤销。
- 自动展示结果应保留返回原运行的路径；用户执行期间已切换任务时，以完成通知和跳转入口避免打断阅读。

### 方向三：结果理解与对比

**用户问题：看到了轨迹和数字，但不容易判断本次结果与修改效果。**

每次运行先提供简洁概览：任务、最终输出、结束原因、可定位的失败步骤、耗时和 token 消耗。详细轨迹继续用于追查依据。

分支对比优先回答三个问题：

1. 改了什么：展示 prompt、工具结果、模型或参数的实际变化。
2. 结果变了什么：并排查看最终输出，并能继续定位相关步骤、工具调用和上下文差异。
3. 消耗变了多少：在相同口径下对比耗时、token 和缓存数据。

实施约束：

- 第一版聚焦两个运行；多臂实验后续复用成熟的对比体验。
- 区分用户修改的位置与后续首次可观察到的行为差异，不自动断言因果关系。
- 共同前缀根据已有分支语义识别；步骤增删或执行路径变化时显示未对齐部分，不能将相同轮次直接视为对应行为。
- 区分本次新增执行消耗、沿链累计增量和继承前缀，避免将累计增量误称为一次完整执行的总成本。
- 缺失数据明确标记未知；token 数不直接等同于金额，价格不完整时不推算确定费用。
- 输出质量首先由用户阅读判断，本轮不引入自动评分或自动优劣结论。

## 3. 第一轮范围

选择一条贯穿三个方向的流程作为首轮交付：

**打开已有运行 → 查看某一步 → 修改工具结果 → 从该处重跑 → 查看新结果 → 与原运行对比。**

使用满足现有重跑条件、具有多步工具调用的示例运行验证流程。原生纯对话运行、代理录制运行另行验证各自支持的操作，界面应体现能力差异。

首轮应包含：

- 主界面信息层级和运行导航调整。
- 步骤阅读与就近编辑入口。
- 重跑前范围确认、执行反馈、失败详情和支持路径的取消。
- 新运行结果概览与两个运行的输出对比。
- 完成、失败、取消、空数据、缺失历史信息等状态设计。

后续扩展到原生创建、代理录制、prompt 修改和模型 A/B，复用统一的状态、结果与导航规则。

实际推进先覆盖真实接入项目及两次运行的清楚对比：修改内容、最终输出、文件差异、错误与本次新增消耗。R2.1 导出和 R3 单环境测试按能力交付接入同一流程，先让用户获得可用结果与验证证据；完整多臂管理和更多图表不能阻塞这条流程。后置指新增扩展，已有模型 A/B 的显示缺陷仍在本轮修复范围内。

R2.1 的导出反馈须沿用路线 §5：只承诺 R1 契约内的普通文件字节保真，清单明确标出未保留状态；历史未记录时显示“未保留（原状态未知）”。不能将导出成功呈现为完整项目状态恢复；R3 如扩展状态契约，导出与界面验收同时更新。

## 4. 推进阶段

| 阶段 | 工作 | 交付物与通过条件 |
|---|---|---|
| P0：现状核查 | 走查首轮流程，记录入口、跳转、状态与数据缺口；核查取消和错误记录能力 | 当前流程图、问题清单、所需数据与执行能力清单 |
| P1：布局与交互验证 | 绘制主界面、步骤详情、执行状态和对比视图；用典型数据推演流程 | 可点击原型或布局草图，以及完整状态表；能从原运行连续走到对比结果 |
| P2：完整流程实现 | 围绕首轮流程补齐布局、反馈、错误信息与结果对比 | 桌面端可操作的完整流程；按职责边界拆分可独立验证的 OpenSpec change |
| P3：验证与扩展 | 观察首次使用者操作，修复主要阻碍；再覆盖其他入口 | 使用记录、验收结果、已知限制和后续待办 |

上表只定义 P0–P3 的工作与交付物，不另定产品排期。路线 §3.1 统一维护“P0–P3 为行、五个产品时点为列”的矩阵；本文件 §3 的第一轮对应其中“现在，与 R1-A 同期”和“现有主流程改造”两列。后续能力接入时重复核查、原型、实现与验证，不把 P3 理解为必须等 R3。具体技术选型与工期在 P0、P1 后确定。新增进度或错误字段时，应同步考虑旧 trace 的兼容性。

### 与隔离重跑和打包的关系

本规划 P0/P1 现在继续推进，已复现且范围明确的界面缺陷在复核后可独立修复；P2 针对现有受支持运行先完成主流程，不以隔离能力为前置。隔离桌面入口和文件视图开发时复用其布局、状态和导航，相关改动顺序集成并共同回归。

A 的桌面修改仅限路线 §3.1 的版本兼容白名单；可用性布局、渲染组件、IPC 或 main 流程改造不能以兼容修正名义并入 A，按 U 或 B/C 的职责分别进入 OpenSpec。

近期先为已归档能力准备一次 K0 自用体验包，不等待本规划全部完成；一组界面缺陷修复或现有主流程改造验收后，打 K1 可用性体验包，用实际 exe 验证。隔离创建、分叉和文件差异完整后，再打 K3 首期候选包。打包基线、版本识别、检查命令和实包验收统一维护在路线 §9.1，本规划不重复定义。

K0 按路线 §9.1 的七项能力清单记录实包可达性；Trace-as-Test 当前属于包/CLI 能力，没有桌面入口，不能记为 exe 验收通过。未知、失败和包外能力须保留说明，不因源码已归档就宣称下载包已支持。便携包体积预算沿用该节保留 Gitee 分发渠道的要求。

## 5. 验收标准

### 使用体验

- 首次使用者在不阅读外部说明、无人代为指路的情况下，能够完成首轮流程。
- 用户能辨认当前运行、当前步骤和正在执行的操作，返回后能继续阅读原内容。
- 提交后有即时反馈；等待、成功、失败与取消状态可以明确区分。
- 失败后能够找到已记录的原因，并判断下一步是调整配置、修改输入还是检查工具。
- 对比时能够指出本次修改内容、两次最终输出的区别，以及消耗指标的含义。
- 代表性桌面窗口尺寸与窄窗口下，主要入口可见，文本不重叠，主要内容可读。

P0 记录当前流程的完成时间、误点和需要提示的次数，P3 使用相同任务对照。首轮建议邀请 2 至 3 名不熟悉当前界面的使用者；结果用于发现问题，不作为统计性结论。若暂时没有外部参与者，需明确标注为内部走查。

这 2 至 3 人可从路线首批 3 至 5 名实际 Agent 开发者中选择。熟悉示例后再观察其真实项目任务，记录接入成本与修复操作成本；按路线 §10 控制学习顺序与重复测试。内部走查、外部任务成功和后续再次使用分别记录，不用“看懂演示”替代产品使用证据。

若只有维护者本人参与，按路线 §10.1 只报告任务完成/未完成及原因；耗时仅作内部排障记录，不用 P0/P3 的时间差证明效率提升或竞争优势。

### 功能与工程

- 覆盖成功、模型错误、工具错误、取消、无数据以及父链或错误信息缺失的适用场景。
- 根据变更风险验证状态流转、取消传播、错误落盘和对比数据口径；布局调整通过实际桌面操作和截图检查。
- 运行项目要求的质量检查，并验证桌面完整构建；现有 CI 构建不包含桌面前端打包，不能替代该项验证。
- 保持封存 trace 不可修改、共享前缀和各类重跑语义不变；新增字段兼容已有记录。

## 6. 本轮暂缓

- 项目分组、标签、收藏及复杂运行管理。
- trace 分享导出、多人协作。
- 自动评价、质量排行榜。
- Trace-as-Test 的完整桌面管理界面。
- 隔离世界真重跑和跨平台发行。
- 与首轮使用问题没有直接关联的大型图表或装饰性动画。

上述内容不并入本轮可用性 change；隔离世界真重跑已作为独立主线推进，其桌面交互需复用本规划成果。“本轮暂缓”不表示项目整体暂停该能力，其余候选按各自路线排序。
