## 二、三条结构性判断（本规划的前提）

### 判断 1 · ⭐「零摩擦接入」与「A/B」之间是断的（定位级）

**链路证据**：

```text
代理录制 → packages/llm-proxy/src/handler.ts:298
           meta: { task, model, source: { kind: "proxy" } }      ← 无 config_hash
                   ↓
         apps/desktop/src/main/proxy-recorder.ts:10
           注释原话：「**无 config_hash**（无源配置可哈希，诚实缺省）」
                   ↓
         packages/replay/src/fork-parent.ts:8
           头注：「prompt fork 与模型 A/B 实验走同一条门禁」
         fork-parent.ts:47-52   proxy 来源 ⇒ 抛「由本地录制代理录制，不支持 prompt fork」
         fork-parent.ts:54-57   缺 config_hash ⇒ 抛「缺少 config_hash，无法作为 … 父 run」
```

⇒ **代理录制的 run 不能当 A/B / prompt fork / tool_result 重跑 的父本**，只能"编辑 messages 重发"。
⇒ **README 已诚实声明这条**（`README.md:126`）——所以它不是"未发现的洞"，而是"**已声明的边界，其代价今天才被量化**"：AniPedia 为了跑一次 A/B，被迫自写 ~120 行 trace 写出器 + 40 行参数 shim + 派生模型 + 预热协议。

**但"无源配置可哈希"这个理由经不起推敲**：`config-hash.ts:5-8` 的输入只有 `{ systemPrompt, tools }`——而**这两样都在代理看到的请求体里**（`messages` 里的 system + `tools` 字段）。也就是说：

> **代理手上其实有算 `config_hash` 的全部原料**，缺的不是数据，是"决定算不算"。

这条把判断 1 从"抱怨"变成一个**可行的技术选项**（见 §三 D-A）。

### 判断 2 · D3（provider 参数透传 + 生效性自检）的证据已经够了

今天累计浮出 **5 条 provider 级静默失败**，全部**不报错**：

| 现象 | 出处 |
|---|---|
| `/v1` 静默忽略 `num_ctx`（顶层/嵌套/字符串三种写法都不认） | 本机实测（dogfood-plan 附录） |
| `think:false` 在 `/v1` 无效，须 `reasoning_effort:"none"` | 本机实测 |
| `/v1` 发 `reasoning`，我们只读 `reasoning_content` ⇒ COT 丢 | `llm-client.ts:195` |
| 预热窗口与臂窗口不一致 ⇒ **静默重载**（1-token 请求耗 4.3s） | 今日实测 |
| `keep_alive` 单位（裸数字串 400 / 数字按秒） | 今日实测 |

原计划把 D3 定为"**等 P3 数据再定**"。**数据已经在手了**，而且全是"静默失败"这种最贵的形态。

### 判断 3 · 代码产出与对话产出的配比已失衡

今天 ReBaseAgent 侧的代码产出只有 ttft 修复（已归档）；**A1/B1/A2/A3 一个都没动**。若继续只维持通信，会形成"对话产出 ≫ 代码产出"。

## 三、决策点（需要你拍）

### D-A · 代理录制的 run，要不要能当 A/B 父本？

| 选项 | 做法 | 规模 | 收益 | 代价 |
|---|---|---|---|---|
| **A-1 关掉裂缝** | 代理录制时从请求体提取 system + tools，用**同一个** `configHash()` 现算并写入 `meta.config_hash`；放宽 `fork-parent.ts` 的 proxy 门禁（或改为"有 config_hash 才拒"） | 小（代理侧 ~10 行 + 门禁 ~5 行 + 文档/spec） | **"只改 `base_url` 录制 → 直接 A/B" 成真**；产品叙事从"两条不通的路"变成一条 | 要动核心门禁（三处：内核 / CLI / 桌面）；需声明"代理 run 做父本"的语义边界 |
| **A-2 守住边界** | 承认"代理 = 抓流量看，不是做实验的起点"；改为**给外部应用一条低成本正道**：trace 写出器支持包（schema 校验 CLI + 最小示例 + 文档），把 AniPedia 那 120 行压到 ~30 行 | 小 | 不动核心门禁；边界清晰 | "零摩擦 → A/B"仍然不通，用户仍要写代码 |
| A-3 不动 | 保持现状（README 已声明） | 0 | 0 | 每次新用户都要重走 AniPedia 那条路 |

**我的倾向：A-1**，理由：① 原料本来就有（`config-hash.ts` 的输入全在请求体里），"无源配置可哈希"的理由不成立；② 它把两个卖点接上了，是**定位级**收益；③ 规模小。**反方**：若你认为"代理抓来的流量不该被当成实验起点"（语义洁癖），那 A-2 也成立，但要把这句话明确写进 README，别让用户自己撞。

### D-B · D3（provider 参数透传 + 生效性自检）是否现在立项？

- 支持现在立项：判断 2 的五条证据都在手，且每一条都是"静默错"；AniPedia 类的本地 Ollama 用户会**必然**踩到。
- 支持继续等：它需要设计"哪些 provider 专属参数允许透传、如何自检生效性"，是**中**规模，且与 A-1/A-2 抢同一段注意力。

**我的倾向：立项，但排在 D-A 之后**（见 §四 排序）。

### D-C · dogfood 与代码工作的配比

- **并行**：dogfood 转异步（他们出父 trace + dry-run，我们一次核对），我们同时开代码工作；
- **串行**：等 P2 跑完再回代码。

**我的倾向：并行**，理由：昨天已论证"dogfood 的剩余量很小且只卡在他们侧"（shim + 写出器 + 派生模型 + dry-run），我们没有可做的事；空等等于浪费。

## 四、推荐排序（含反方观点）

| 序 | 项 | 规模 | 为什么排这里 |
|---|---|---|---|
| **1** | **B1 · GitHub Actions CI** | 小 | 今天刚做出"434 全绿 + biome 0 + validate 10/10"的干净基线，**趁热固化成安全网成本最低**；之后所有改动都受它保护。它是"没它也行、有它省事"的典型，越早越省 |
| **2** | **D-A 的决定 → 落地 A-1（或 A-2）** | 小 | 定位级裂缝；dogfood 正在被它卡；原料已具备 |
| **3** | **D3 · provider 参数透传 + 生效性自检** | 中 | 证据已足；止住"换 provider 就静默错"这类复发 |
| **4** | **A1 · 原生 run 创建入口**（含 D5 桌面端 `tools` 门禁缺陷） | 小 | dogfood 已证明"没有它也能推进"（他们手写 trace 跑通了链路）⇒ 它解决的是**桌面端体验**，不是能力有无。且 A-1 若成立，它的必要性进一步下降（代理 run 也能当父本） |
| **5** | **A2 共享前缀重跑** / **A3 隔离世界真重跑** | 中 | README 里"成本约 1/4"目前是**承诺不是事实**，属兑付问题；排在能力补齐之后 |
| — | 工程债 | 小 | 我方：`openspec` 2 条 long-requirement INFO、dogfood-plan 拆分（31 条修订）；对方：`keep_alive` 单位、`answer.py` 注释 |

**反方观点（我认这个可能成立）**：若你认为"**本地优先的价值在'看得清'而不在'跑实验'**"，那 D-A 应该降级、D3 也降级，优先把 A3（隔离世界真重跑）做出来——因为它才是"时间旅行"与 LangSmith 的真正差异点（LangSmith 不做真重跑）。**这是一个产品定位选择，不是工程判断**，所以必须由你拍。

## 五、明确不做（Non-goals）

- **不做 agent 构建器 / 平台化**（历史已否，2026-09-04）
- **不追 LangSmith 的功能面**（我们是本地优先 + 时间旅行，不做云协作/标注）
- **不为变现破坏"本地不出机器"**
- **不在本规划里定 provider 参数白名单**（属 D3 的设计内容）
- **不重算历史 trace**（`.rebaseagent/` 本地产物，无兼容负担）
