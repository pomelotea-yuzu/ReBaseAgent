## 1. 目标与取舍

ReBaseAgent 的近期目标是成为一个有辨识度、容易体验、值得开发者收藏和推荐的开源项目。付费转化、商业收入和团队版销售不作为本轮规划的衡量指标。

历史文档 `docs/product/product.md` 曾讨论商业形态。本次目标已明确为免费开源传播；后续实施以维护者本次意图为准，历史商业设想不视为当前待办。

希望形成的传播路径：

**看到中文案例 → 从 Gitee 下载体验包和示例 → 看懂修改与文件变化 → 尝试受支持的真实任务 → 反馈、再次使用或推荐。**

首轮先验证案例能否看懂、包能否使用、开发者是否愿意尝试。真实项目接入、修复验证和后续结果导出继续作为产品目标；导出、真实测试和效率对照不作为 K1 预热的前置条件，也不提前写入首轮功能承诺。

Star 是传播结果指标；产品开发优先看接入、真实任务完成和后续独立问题中的再次使用。看懂内置示例是上手信号，不能替代实际项目接入；关注增长也不能单独证明优于竞品。项目现有能力具有传播潜力，但尚不能据此预测 Star 数量。

## 2. 首要受众与传播主题

### 首要受众

- 优先面向中国大陆维护多步文件或代码 Agent 的独立开发者和小团队；首批动手试用者使用 Windows x64，真实项目接入聚焦一种能验证完整契约的技术栈。
- 对 Agent 调试、上下文工程、可复现问题与本地开发工具感兴趣的开源用户。
- 曾因工具结果错误、prompt 调整或多步调用成本而反复排查的人。

优先让有具体问题的人理解价值，再通过可读的演示吸引更广泛的开发者关注。

### 主传播主题

建议保留“Agent 的时间旅行调试器”作为定位，并用具体场景解释：

> Agent 写错文件了？改掉某一步的工具结果，在隔离副本中继续跑，再查看文件发生了什么变化。

K1 首轮围绕“查看原运行与错误文件 → 定位工具结果 → 修改并隔离续跑 → 查看新分支的检查点和文件变化”制作案例。每次文件 diff 的两侧含义以实际检查点为准；可以分别打开父、子运行查看，不把它描述为已支持任意两个运行的文件 diff。该案例须在 K1 实包走通，不能仅凭 U2 的阅读验收推定执行流程也通过。

案例优先取自可公开的真实项目；暂时只有受控示例时明确标注，仍可用于功能预热和上手试用，但不能称为外部用户修复或竞争证据。后续随接入、导出与真实测试交付，再升级为“真实项目失败 → 修复验证 → 带走修改”。隔离 prompt 按案例需要提供最小功能，完整隔离模型 A/B 扩展后置，不否认已有普通模型 A/B 能力。

对外表述需与实现一致：

- 区分修改工具结果后的续跑与修改启动 prompt 后的从头重跑。
- 默认重放不代表外部文件、数据库或 API 状态完整回退。
- Trace 保存在本地；真实模型请求仍按用户配置发往服务商，不能笼统宣称所有数据始终不离开机器。
- 缓存、费用和耗时改善使用实测条件与区间，不能将某个示例的收益推广成所有任务的保证。
- 对同类工具的比较基于具体能力与验证日期，不沿用未经核实的“其他工具只能看、不能改”说法。
- 文件导出交付后沿用路线 §5 的 R1 字节保真边界，公开案例保留导出清单中的“未保留”及“原状态未知”说明；K1 不提前宣传导出和真实测试，R3 未扩展并验收状态契约前不宣传完整项目环境恢复。

## 3. 四项核心工作

### A. 做一个 30 至 60 秒的真实演示

演示案例优先从实际接入项目中选取，有明确错误和预先规定的正确性判据。首期可以展示错误工具结果导致的错误文件产物及续跑修复；测试能力完成后展示真实失败与通过的测试记录。库存回答等合成案例可作入门素材，但不能代替真实开发任务的竞争证据。

| 片段 | 展示内容 | 观众应理解的事情 |
|---|---|---|
| 开头 | 原任务、不符合预期的文件产物及相关回答 | 这个工具解决什么问题 |
| 定位 | 打开包含错误信息的工具结果 | 问题出现在哪一步 |
| 修改 | 修改工具结果，确认续跑范围 | 可以改变某一步输入 |
| 执行 | 展示真实重跑反馈 | 修改产生了新分支 |
| 结果 | 打开新分支，查看检查点文件变化，按需回看原运行与输出；消耗有实测才展示 | 修改带来了什么变化，依据是什么 |

交付物：一份可复现案例、原始录屏、30 至 60 秒中文短视频或动图、封面静态图、中文简介；注明包版本与案例来源。英文材料按后续需求准备。

验收要求：

- 观众不依赖口头讲解，也能说明“改了什么、结果如何变化”。
- 案例使用可公开的数据；录制前整理窗口和数据列表，避免混入私人内容。
- 镜头来自可下载版本实际支持的操作；剪辑加速或省略等待时明确标注。
- 示例不能保证每次模型输出逐字一致，验收围绕可观察行为和案例判据。
- K1 实包验收后即可录对应预览版演示；U3–U8 后续改变流程时更新素材。用于正式发行的演示按 K3 完整流程与实包验收条件准备，视频和下载始终指向同一个版本。

### B. 提供无需配置 API 的示例体验

第一版优先提供整理好的原运行、修改后分支和必要父链，使用户无需密钥即可查看案例、定位修改点、比较已录制的结果。

首轮优先评估独立示例数据包，附中文任务概述、预期结果与经过验证的打开步骤；按现有数据目录规则使用独立副本，包含原运行、修改后分支、完整父链和所引用的文件附件。不得覆盖用户已有数据，也不能只发 JSONL 导致文件不可读。数据包与 K1 一起在 Gitee 提供，实测首次打开后才能列为可用入口。

内置示例或“打开示例”按钮作为后续改善；若现有路径足以完成少量试用，不为首轮宣发新增完整教程系统。示例准备和载入验收是独立待办，不属于 U2 已交付内容。

需要明确的体验边界：

- 免配置体验覆盖查看和理解已录制案例；实际生成新的模型分支仍需用户配置并承担相应调用费用。
- 示例可以展示既有修改前后结果，不能将预录结果伪装成用户刚刚发起的真实重跑。
- 使用固定的公开测试材料，避免依赖用户电脑上的特定路径、凭据或外部状态。
- 首轮不新增完整教程系统或另一个执行引擎。

验收要求：全新数据目录下，用户能找到示例并看懂修改前后的差别；没有 API key 时不自动产生网络模型请求。

### C. 完善首次使用流程

实施依据：

- `docs/engineering/plans/2026-09-15-usability-improvement-plan.md`
- `docs/engineering/plans/2026-09-21-ui-change-split-plan.md`
- `docs/reviews/2026-09-21-ui-usability-walkthrough.md`（问题基线，不能充当整改后的验收结果）

按当前 U 拆分实施，不再把全部 UI 问题笼统列为“布局改版未开始”：U1 已完成并归档，U2 正在开发和验收；完成状态以各 change 的任务与证据为准。

| 交付节点 | 对宣发和试用的意义 | 尚需明确的边界 |
|---|---|---|
| U1 + U2 验收，K1 实包通过 | 运行概览、步骤与文件阅读具备首轮展示基础；按实测支持路径开展小范围试用 | U3 草稿保护、U4–U5 执行状态和结果流程、U6 部分读取、U7 对比、U8 录制/实验体验仍待完善 |
| U3–U5 验收 | 扩大主动创建、编辑和重跑的试用，减少草稿和执行反馈阻碍 | 仍需核对当时的比较入口与异常路径，不宣称完整新 UI 已完成 |
| 完整流程和相应可用性验收，K3 实包通过 | 准备正式发行与更广范围的中文介绍 | K3 按实际流程验收触发，不机械地要求所有后续能力完成；若宣称完整新 UI 范围则须满足相应 U 验收 |

首轮重点是看懂“改了什么、文件如何变化”，按现有可用入口演示；两条运行的完整新对比体验由 U7 推进，现有四条对比指标仍须回归。阅读验收不能替代创建、分叉和文件差异全流程验收。

### D. 整理适合传播的仓库与发行内容

建议的 README 阅读顺序：

1. 项目名称、一句话定位、实际界面演示。
2. Windows x64 支持范围、Gitee 具体版本下载入口与示例；免费查看案例的最短路径。
3. 三个典型用途：查问题、改一步验证、对比结果。
4. 按需要展开的接入方法：原生运行、代理、SDK。
5. 当前边界与数据处理方式。
6. 技术架构、开发方式、贡献入口和详细文档。

已有 README 的完整技术内容可拆到详细文档，保证首次访问能先看懂用途。

以中文 README、中文演示字幕和中文发行说明为首轮材料。英文 README、英文社区投稿和界面国际化后置，不作为首轮发布前提。

仓库、下载、演示图片/视频、示例和反馈须形成大陆用户可用的完整路径；关键素材不依赖 GitHub 图片、raw 或 Release 资源。Gitee Releases 为下载主入口，Issues 为公开反馈主入口；核验匿名浏览及下载，若下载或反馈需要登录须如实写明。当前 README 中“数据不出机器”“现有工具只能看”等绝对表述，在准备发布材料时按 §2 校准；新案例不能仍引导下载不含对应能力的旧 K0。

发行内容包含可下载产物、版本说明、示例及清晰的平台支持说明。当前已有 Windows x64 便携版；其他平台的用户应能先看演示、理解现状，跨平台构建根据实际反馈再排序。

下载包能否宣称包含某项能力，以路线 §9.1 的实包验收记录为准；K0 逐项核对七项归档能力，Trace-as-Test 当前是包/CLI 能力，不能作为 exe 已提供的操作宣传。Gitee 现为主要渠道，便携包继续沿用单文件严格小于 `100,000,000` bytes 的发行预算；示例附件也须核对当时平台限制。

## 4. 面向大陆用户的分阶段宣发

### 当前优先：U8 后录制，10/07 争取完成参赛提交

目标 10/02 前完成 U1–U8 验收和跨入口回归，10/03 完成新参赛包及案例验收，10/04–10/05 录制、剪辑并完成 PDF 与链接交付，10/06 复核，10/07 实际提交。案例、脚本、PDF 草稿和报名手续现在与开发同期推进；这是一份目标排期，不是完成承诺。各阶段状态与风险检查见比赛方案，赶进度不降低验收要求。

参赛成片建议 3–5 分钟，包含 U1–U8 的新包与视频保持一致。K1 交付后可用于内部验证和试拍；U8 完成不自动代表 K3 或正式发行通过，仍按路线 §9.1 实包验收。下述阶段一至四是社区传播安排，首批 3–5 人试用及第 7/30 天复盘不作为 10/07 参赛提交的前置条件；仅上传参赛材料不算已开展社区试发。

### 阶段一：现在准备案例与中文材料

可以推进的工作：

- 继续完成 U2 实施、实机验收和质量检查。
- 整理一个公开案例、完整示例数据与 30 至 60 秒演示脚本，标明真实项目或受控示例来源。
- 草拟中文 README、K1 发行说明与试用介绍，列清预览版边界。
- 核对 Gitee 仓库、Releases、素材与反馈路径，选定一个受众匹配的中文社区。
- GitHub 申诉按需跟进，不占用首轮宣发的关键路径。

材料准备现在即可开始；涉及 U1/U2 新界面的可下载演示待 K1 实包验收后录制。不要求先完成 U3–U8、导出、真实测试或竞品效率对照。

### 阶段二：U2 与 K1 验收后，小范围预热和试用

启动条件：

1. U2 剩余实机场景、只读回归、质量检查和逐场景证据完成；不能只看实现任务勾选。
2. 按路线 §9.1 打出 K1，在真实 exe 验证首次启动、示例阅读、案例中的创建/分叉/文件差异、错误状态和返回路径；记录版本、提交、哈希及已知限制。
3. 示例可在独立数据目录中打开，父链和附件完整；无密钥查看不会自动发起模型请求。
4. Gitee 对应版本、下载文件、示例和中文说明可访问，演示与包能力一致；记录登录要求。上传与链接核验实际完成后再对外招募，不把文案中的预定链接当作已发布。

先在一个匹配的中文渠道发布预览介绍，指向 Gitee，计划招募 3 至 5 位维护真实 Agent、但不熟悉当前界面的开发者；与可用性和接入主线共用参与者。首轮不要求预先完成这批人的真实项目修复和再次使用记录，试发用于开始收集这些证据。

试用先用示例熟悉操作，再在已验证支持的技术栈下尝试参与者的真实任务。记录下载/启动、示例理解、定位修改点、查看文件变化是否成功，以及卡点和所需提示；真实模型调用按参与者配置与预算执行。真实项目接入、修复和后续再次使用分别记录；导出和真实测试未交付时标为不支持，不将其缺失等同首轮试用失败。只有示例查看时标为上手验证。

记录卡住的位置、需要维护者提示的次数和缺少的信息，优先修复明显阻碍。

实际竞品对照采用路线 §10.1 的同任务口径，先核对版本、套餐与能力，保留失败和不支持结果。首次使用后建议在 7 至 14 天收集自愿反馈，记录是否在后续问题中主动使用；未遇到新问题时记为未知。这是试用安排，不创建自动提醒或消息发送。

若参与者仅维护者本人，内部对照只报告完成/未完成及原因，耗时不列为效率或竞争优势证据；路线 E2 的外部效率对照保持待验证，宣传材料不得把内部重复操作的时间差写成产品优势。

### 阶段三：完整流程通过后扩大中文传播

小范围试用暴露的明显阻碍已处理，并满足路线 K3 的完整流程及相应可用性、实包验收条件后，围绕一个可下载版本扩大介绍。无需等待 GitHub 恢复，也不以全部后续功能齐备为条件；效率或竞品优势仍须另有对应证据。

| 渠道 | 适合内容 | 节奏建议 |
|---|---|---|
| Gitee README、Releases、Issues | 中文演示、下载、示例、版本变化和反馈 | 所有介绍的主要落点，版本与素材同步 |
| V2EX、掘金或相关 Agent 开发者社区 | 一次调试案例、实现思路与试用结果 | 先选一个，处理反馈后再扩展 |
| B 站或已有个人内容账号 | 中文短演示和案例操作记录 | 有对应素材和维护精力时补充，不要求全平台铺开 |
| 技术文章 | 隔离续跑、共享前缀及实现边界 | 作为后续深入内容，结论附条件与证据 |

以上为渠道候选，发布前核对当时规则与受众；具体文案和时点按 K 包验收与反馈安排。Show HN、Reddit 和英文材料后置，不属于本轮必做项。本文不代表已执行对外发帖或邀请。

初次介绍后预留维护时间回复问题、修正下载或接入阻碍，再根据反馈扩展渠道。

### 阶段四：持续提供可分享的进展

后续每次传播围绕一个真实进展：一个用户案例、一项明显体验改进、一段有证据的技术解释，或一个可复现的问题解决过程。

可增加简洁的问题反馈模板与贡献说明，将适合外部参与的任务标注出来。提交问题不应要求公开带密钥或私人业务内容的完整 trace。

优先维持可下载版本与文档的一致性，逐步形成持续更新和响应反馈的习惯。

GitHub 若恢复，再匿名核对仓库、素材、Release 和下载，按需求增加镜像或海外传播。恢复不会自动把主渠道切回 GitHub，也不影响已经开展的 Gitee 宣发与复盘。

## 5. 衡量方式

| 指标 | 记录方式 | 用途 |
|---|---|---|
| 真实接入与修复 | 技术栈、接入改动/用时、帮助次数、修复判据；导出交付后补产物记录 | 产品开发优先指标，判断能否用于已有项目 |
| 相对原有方法的效率 | 按路线 §10.1 同任务对照，分列一次性接入和每次修复成本，保留失败；仅维护者参与时不形成效率证据 | 限定到已验证任务判断竞争价值，不预写“全面领先” |
| Gitee Star 总量及净增长 | 首次试发前记录基线，发布后按周记录；GitHub 恢复后另列 | 判断主要渠道的关注增长，不将跨平台 Star 相加为独立用户 |
| 仓库访问和来源 | 使用 Gitee 与投放渠道当时可提供的数据；无法获得时记为不可得 | 判断介绍是否带来有效访问 |
| 发行版下载 | 使用发行渠道可提供的数据，按渠道分别记录 | 判断是否有人愿意尝试 |
| 示例任务完成情况 | 小范围试用记录 | 找到首次使用阻碍 |
| 有效反馈与推荐 | Issue、讨论及参与者自愿反馈 | 理解实际需求与传播原因 |
| 再次使用 | 参与者自愿反馈是否在后续独立任务中主动使用，区分无新任务 | 产品开发优先指标，判断是否进入实际工作流程 |

Star、访问与下载不等于独立用户数，也不天然属于同一批人，不直接计算为精确转化率。不为增长统计额外引入应用遥测。

可以把 Gitee 首批 100 个真实 Star 作为观察节点；达到后再判断下一阶段目标。首轮更直接的目标是完成 3 至 5 人试用，记录能否打开示例、看懂变化和完成声明支持的操作。人数和 Star 都不是增长预测或交付承诺，未达到也应按反馈复盘。

首轮复盘建议在 Gitee 版本可下载且首条中文预览介绍实际发布后的第 7 天和第 30 天进行，比较基线、下载、Star 和实际反馈；扩大传播时另记渠道与日期。无需等待 GitHub 恢复，不因暂无真实任务或再次使用记录推迟首轮复盘。

根据现象调整：

- 访问很少：检查分发渠道、介绍标题和受众匹配。
- 有访问但没人理解用途：调整开头定位与演示案例。
- 有下载但无法完成示例：优先修接入、布局和操作反馈。
- 有收藏但很少实际使用：进一步寻找高频场景，不能仅凭 Star 判断使用需求。
