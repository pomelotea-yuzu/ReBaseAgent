# ReBaseAgent 多模型协作工作流

## 1. 目的

ReBaseAgent 采用按职责分工的多模型工作流，在控制 API 成本的同时保持设计质量、代码质量和项目约束的一致性。

核心流程：

规划 → 审阅 → 人工确认 → 实现 → 验证 → 归档 → 交接

三种模型各自负责不同阶段：

| 角色 | 模型 | 主要职责 |
|---|---|---|
| 规划者 | GPT-5.6-SOL | 理解产品目标、核对代码与 spec、拆 change、编写 OpenSpec 规划文件 |
| 审阅者 | DeepSeek-V4Pro | 对照实际代码审查方案，发现架构、兼容性、安全和测试缺口 |
| 实现者 | GLM-5.3Flash | 按已确认的方案修改代码、补测试、运行门禁、汇报实现结果 |

人工负责人负责确认范围和关键决策，并在需要时执行外部操作，例如推送远程仓库、提供真实 API 凭证或确认发布。

## 2. 总体原则

### 2.1 规划、审阅、实现分离

- 规划者不直接实现代码。
- 审阅者默认只读，不在审阅过程中偷偷改代码或修改设计结论。
- 实现者不擅自改变已确认的行为语义；发现设计问题时必须回到规划阶段修订。
- 人工负责人在规划和审阅之后确认，确认前不进入实现阶段。

### 2.2 项目文件优先

每个模型开始工作前，先读取：

1. HANDOFF.md
2. openspec/config.yaml
3. openspec/specs/
4. 对应的 openspec/changes/archive/ 设计文件
5. docs/product/product.md
6. 相关源码、测试、构建脚本和 git 状态

若交接文档、README、旧会话记录和当前代码冲突，以当前代码、主 spec 和最新归档 change 为准；冲突必须在报告中指出，不能静默选择。

### 2.3 所有产出使用中文

代码注释、文档、OpenSpec 文件、测试描述、提交信息和模型间交接均使用中文。协议字段、API 名称、TypeScript 类型名等既有英文标识保持原样。

### 2.4 不绕过 OpenSpec

涉及用户可见行为、数据格式、IPC、replay、分支关系或架构不变量的改动，必须先有 change 规划，再实现。实现中发现 spec 不正确时，暂停实现并回到规划阶段修订。

## 3. 阶段一：GPT-5.6-SOL 规划

### 输入

- 用户需求
- 当前 HANDOFF.md
- 项目产品方向与路线图
- OpenSpec 配置、主 spec、归档 change
- 相关源码、测试、构建脚本和 git 状态

### 工作内容

1. 判断需求属于现有 change 的延续还是新的 change。
2. 检查现有架构不变量和历史设计决策。
3. 识别真实代码边界，不以 README 或旧计划代替代码核实。
4. 拆分能力范围、非目标、保真度边界、风险和验收门禁。
5. 创建完整 OpenSpec 规划文件：
   - proposal.md：为什么做、做什么、不做什么
   - specs/<capability>/spec.md：行为契约和 scenario
   - design.md：技术决策、数据流、兼容性和失败语义
   - tasks.md：每个任务控制在约 2 小时内，并对应可验证验收标准

### 规划者禁止事项

- 不修改 packages/、apps/ 下的产品代码。
- 不直接运行 apply、实现或归档。
- 不把未确认的重大选择伪装成既定事实。
- 不引入 config.yaml 未允许的新依赖而不说明理由。

### 输出格式

规划完成后必须说明：

- change 名称和文件位置
- 主要行为决策
- Non-goals
- 保真度边界
- 待人工确认的决策
- 验收门禁
- 当前尚未实现

## 4. 阶段二：DeepSeek-V4Pro 审阅

审阅者不只检查文字质量，而是逐条对照实际实现和测试。

### 审阅顺序

1. 读取 proposal、design、spec delta、tasks。
2. 读取相关源码和现有测试。
3. 对照 config.yaml 和主 spec 检查是否越界。
4. 检查数据格式、父子关系、错误处理、兼容性、密钥和隐私边界。
5. 检查每个 scenario 是否能被实现和测试验证。
6. 检查 tasks 是否存在遗漏、重复或无法在约 2 小时内完成的任务。

### 审阅重点

- 是否把“共享前缀”“完整新轨迹”“代理单请求分叉”等不同语义混在一起。
- 是否破坏 JSONL 不可变、派生数据不累积、renderer 无 fs、IPC 信封和 zod 校验等不变量。
- 是否错误地从不可逆数据推断配置或用户输入。
- 是否把理论成本、缓存命中或 replay 保真度说成确定事实。
- 是否覆盖旧数据、缺失父 run、成环、失败中断和空操作。
- 是否有明确的零 API 测试和 GUI 冒烟路径。

### 审阅结果格式

每条问题按优先级报告：

- P0：阻止实现，可能造成数据损坏、错误语义或严重安全问题。
- P1：应在实现前修正，否则会导致主要场景不可用或难以维护。
- P2：可后置，不阻止当前 change。

每条问题必须包含：

- 文件和位置
- 观察到的代码事实
- 为什么与方案冲突或存在风险
- 建议的具体修正

审阅者默认不修改方案文件。审阅结论返回规划者处理。

## 5. 阶段三：规划修订与人工确认

出现以下情况时，必须由规划者修订 proposal、design、spec 或 tasks：

- 审阅者提出 P0 或 P1。
- 行为语义、数据结构、IPC 契约或保真度边界发生改变。
- 发现当前 spec 与代码事实冲突。
- 需要新增依赖、放宽权限或扩大 Non-goal 范围。

规划者修订后重新交给审阅者；重大语义原则上至少完成一轮“修订 → 复审”。

人工确认至少要明确：

- 是否接受 change 范围
- 是否接受关键架构决策
- 是否接受成本和保真度边界
- 是否允许进入实现

未经确认，不运行实现阶段。

## 6. 阶段四：GLM-5.3Flash 实现

实现者以已经确认的 OpenSpec 文件为唯一工作合同。

### 实现顺序

1. 阅读当前 change 的全部规划文件和审阅结论。
2. 检查工作区是否存在用户未提交的改动，避免覆盖。
3. 按 tasks 顺序实现，优先完成纯函数、数据契约和测试。
4. 保持已有 API、数据格式和错误语义兼容。
5. 每完成一组任务就运行对应的局部测试。
6. 完成后运行项目门禁和必要的 GUI 冒烟。

### 实现者禁止事项

- 不擅自扩大功能范围。
- 不静默修改 spec 已写死的语义。
- 不为了通过测试删除或弱化既有校验。
- 不把真实 API 调用混入可离线完成的单元测试。
- 不修改用户未授权的远程仓库状态。

### 发现设计问题时

实现者发现以下问题必须暂停相关实现并回报：

- 现有设计无法由当前代码结构安全实现。
- spec 与现有行为矛盾。
- 需要改变 trace 格式或 IPC 契约。
- 需要新增依赖或改变权限边界。

处理顺序是：

实现者报告 → 规划者修订 → 审阅者复审 → 人工确认 → 继续实现。

## 7. 阶段五：验证、归档与交接

### 实现完成后的验证

根据 change 影响范围执行：

- Biome 检查
- 双端 TypeScript 检查
- Vitest
- electron-vite build
- GUI / Playwright 冒烟
- openspec validate --all --strict

所有失败都要区分为代码问题、环境问题或外部权限问题，不能只报告“测试失败”。

### 归档前检查

- 每个 scenario 都有测试、fixture 或明确的人工验收记录。
- proposal、spec、design、tasks 与最终实现一致。
- 主 spec 已同步。
- README、发布说明和限制描述没有明显过期。
- 不存在未解释的临时文件、调试数据或密钥。

确认后再执行 archive。归档提交信息使用中文。

### 交接内容

实现者完成后更新交接材料，至少包含：

- 完成的 change 和提交
- 测试与构建结果
- 尚未完成的任务
- 已知限制和真实验证边界
- 下一步候选
- 环境坑和可复用命令

### 规划 → 审阅

~~~text

已核实的代码事实：
关键决策：
Non-goals：
保真度边界：

~~~

### 审阅 → 规划

~~~text

P0：
P1：
P2：
已确认无问题的部分：
必须修改的文件：

~~~

### 规划 → 实现

~~~text
change：
已确认的范围：

~~~

~~~text

未完成：
已知限制：

~~~

## 9. 成本控制与降级规则

- 规划阶段使用 GPT-5.6-SOL，重点投入在架构判断和边界定义，不重复生成相同方案。
- 审阅阶段使用 DeepSeek-V4Pro，优先做针对性代码核查，避免无关目录的全量分析。
- 实现阶段使用 GLM-5.3Flash，任务按小步提交和局部测试推进，减少返工。
- 已确认的设计不重复规划；只有需求、代码事实或审阅结论发生变化时才重新规划。
- 模型不可用时，不允许由另一模型无记录地越权接替。接替模型必须读取已有交接材料，并在输出中标明接替原因与未覆盖的检查范围。
- API 成本、网络权限或真实凭证不足时，优先完成纯函数、离线 fixture、mock 测试和文档；不得为了“跑通”而提交真实密钥或绕过本地优先边界。

## 10. 当前项目的默认执行方式

以后新增或扩展功能，默认采用：

1. GPT-5.6-SOL 创建或修订 OpenSpec change。
2. DeepSeek-V4Pro 对照源码审阅并提出分级问题。
3. GPT-5.6-SOL 吸收审阅意见，直到方案可实现。
4. 人工负责人确认范围。
5. GLM-5.3Flash 执行 apply、测试和构建。
6. GPT-5.6-SOL 或人工负责人检查最终结果，执行 archive 与交接。

本流程不改变项目既有的本地优先、中文产出、OpenSpec 驱动和 JSONL 不可变等长期约束。
