# 治理与维护安排

核查日期：2026-09-27。本文补充项目研发协作方式。现有 [贡献指南](../../CONTRIBUTING.md)、[行为准则](../../CODE_OF_CONDUCT.md)、[安全策略](../../SECURITY.md) 和 [开发工作流](workflow.md) 仍是对应事项的入口。下文明确标注待落实事项，不把规划写成已有社区运营结果。

## 当前基础

项目目前按单一维护者主导的方式运作。仓库已有 MIT 许可证、贡献指南、行为准则、安全策略、GitHub/Gitee Issue 与 PR 模板，以及 Gitee Go 的 [质量门禁配置](../../.workflow/ci.yml)。本轮仅核查文件存在及内容，没有验证近期线上流水线执行情况。

目前材料不足以证明已有稳定的外部维护团队、持续的社区响应统计、组织资助或长期资金保障。没有数据的指标保留为未建立，不用文档数量替代实际运营。

## 职责与决策

| 角色 | 职责 | 当前承担方式 |
|---|---|---|
| 维护者 | 确定范围、接受变更、处理发布和安全事项 | 当前 owner；账号见根安全策略 |
| 贡献者 | 提交问题、文档、测试或代码，说明来源和验证情况 | 可经 Issue/PR 参与，无须先取得维护者身份 |
| 审阅者 | 核查行为契约、风险、证据与第三方来源 | 按具体改动邀请；尚无独立常设团队 |

行为语义变化继续遵循先 proposal、后实现的 OpenSpec 流程。常规文档修正可直接提交聚焦的 PR；新增功能、修改副作用边界、数据格式或兼容性承诺必须留下设计依据和验证记录。

意见分歧应回到可复现问题、兼容性和验证成本。维护者记录最终选择及理由；无法取得独立审阅时，明确记录自审和残余风险，不声称已经多人批准。自动化工具可以协助检查，接受变更和发布责任仍由维护者承担。

## 贡献闭环

1. 问题报告写明版本、环境、最小复现与预期/实际行为。敏感材料不进入公开 Issue。
2. 维护者先判断类型、影响和能否复现，再决定是否进入变更范围。拟采用“待复现、已确认、处理中、待验证、已关闭”的状态含义；具体标签配置尚待核实。
3. PR 说明解决的问题、行为变化、验证与限制，并链接关联 Issue 或 change。第三方代码、图标、示例与数据应说明来源和许可；不能证明来源时先不合入。
4. 代码贡献按项目 MIT 许可接收，第三方内容保留原许可证与声明；这不是把第三方作品重新许可为 MIT。当前未建立 CLA/DCO 自动化，不宣称已签署或强制执行。
5. 问题关闭时注明修复提交/版本或不能处理的具体原因；重复项链接已有记录。跨 GitHub/Gitee 的同一问题应互相引用，避免两边给出矛盾结论。

普通 Issue/PR 暂不新增固定响应时限。安全策略中已有“通常 3 个工作日内回应”的表述，本文不把它扩展为所有请求的服务承诺。**安全联络渠道仍需落实**：现文档提及的 GitHub 通用私信不是可依赖渠道，私密漏洞报告是否启用也未验证。维护者应先验证一个实际可达的私密入口，再同步根安全策略；未完成前不能声称安全报告闭环已可用。

## 发布与兼容性

已有贡献指南要求运行 `pnpm check:ci`。发布记录还应包含目标平台、源码提交、锁文件、产物哈希、变更说明、已知限制及实际测试结果。环境导致某项检查不能执行时，必须说明替代检查和未覆盖部分。

当前打包目标为 Windows x64。新增平台、破坏数据格式或更改旧轨迹读取行为时，应另行明确兼容策略与迁移验证。版本支持范围以根安全策略为准，本文不新增长期维护版本承诺。

第三方许可证检查应覆盖实际发行内容，包含被打进前端 bundle 的依赖以及 Electron/Chromium 附带声明。源代码使用 MIT 不代表所有依赖都是 MIT。参见 [依赖核查报告](audits/2026-09-27-dependency-licenses.md)。

## 持续维护计划

以下是建议执行顺序和完成条件，不是已承诺日期。默认由当前维护者协调；任务确定后再在对应 Issue/change 中落实负责人和范围。

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| 当前文档阶段 | 记录能力边界、官方对照、许可证输入和实验方法 | 文档可导航、来源可查、事实与假设分开 |
| 下一次发布准备 | 核实私密报告渠道；核对发行物第三方声明；记录构建与运行结果 | 有可验证渠道、有产物检查记录，问题在发布前处理 |
| 执行环境空闲后 | 按一致性实验方案做受控验证，随后开展真实任务研究 | 有原始样本、失败记录、可复核结论 |
| 后续稳定迭代 | 优先处理数据完整性、错误诊断、兼容性和高频使用阻碍 | 每项可追溯至问题、实现和验证；依赖更新有回归依据 |
| 出现持续贡献者后 | 为明确模块引入第二维护者，逐步交接审阅和发布能力 | 有连续贡献记录、交接说明、实际完成的独立维护任务 |

单一维护者是当前持续性风险。缓解方式包括可重复构建、清晰的数据格式和错误语义、可运行的测试、发布步骤和最小权限交接；这些只能降低交接成本，不能替代实际的人力和时间投入。

建议每次发布记录未解决缺陷、Issue 首次响应与关闭时长、外部贡献与维护者投入。没有记录时标记“未统计”，不补造历史数字。维护投入长期不足时，应公开缩小维护范围或标记维护放缓，并更新支持策略，而不是继续承诺无法执行的路线图。
