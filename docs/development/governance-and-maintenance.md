## 当前基础

项目目前按单一维护者主导的方式运作。仓库已有 MIT 许可证、贡献指南、行为准则、安全策略、GitHub/Gitee Issue 与 PR 模板，以及 Gitee Go 的 [质量门禁配置](../../.workflow/ci.yml)。本地另已新增 [GitHub Actions 配置](../../.github/workflows/ci.yml)，尚未在线验证。本轮仅核查文件存在及内容，没有验证近期线上流水线执行情况。

目前材料不足以证明已有稳定的外部维护团队、持续的社区响应统计、组织资助或长期资金保障。没有数据的指标保留为未建立，不用文档数量替代实际运营。

## 职责与决策

| 角色 | 职责 | 当前承担方式 |
|---|---|---|
| 维护者 | 确定范围、接受变更、处理发布和安全事项 | GitHub `pomelotea-yuzu` / Gitee `yuzu-tea-duck` |
| 贡献者 | 提交问题、文档、测试或代码，说明来源和验证情况 | 可经 Issue/PR 参与，无须先取得维护者身份 |
| 审阅者 | 核查行为契约、风险、证据与第三方来源 | 按具体改动邀请；尚无独立常设团队 |

行为语义变化继续遵循先 proposal、后实现的 OpenSpec 流程。常规文档修正可直接提交聚焦的 PR；新增功能、修改副作用边界、数据格式或兼容性承诺必须留下设计依据和验证记录。

意见分歧应回到可复现问题、兼容性和验证成本。维护者记录最终选择及理由；无法取得独立审阅时，明确记录自审和残余风险，不声称已经多人批准。自动化工具可以协助检查，接受变更和发布责任仍由维护者承担。

决定记录在关联 Issue/PR 或 OpenSpec change 中，至少包含问题、采用方案、主要取舍和验证要求。涉及隐私或安全细节时只公开必要结论，证据按私密流程保存。贡献者可以在原记录提出新的事实和替代方案申请复议；当前没有委员会投票或独立申诉机构。

仓库权限按具体职责授予。持续贡献不自动授予合入或发布权限；增加维护者时应公开职责范围、交接内容及生效时间，实际权限另由现有维护者配置。

## 贡献闭环

1. 问题报告写明版本、环境、最小复现与预期/实际行为。敏感材料不进入公开 Issue。
2. 维护者先判断类型、影响和能否复现，再决定是否进入变更范围。按下表说明当前状态；远程标签尚未核实，可以先用正文或评论记录，不依赖标签自动化。
3. PR 说明解决的问题、行为变化、验证与限制，并链接关联 Issue 或 change。第三方代码、图标、示例与数据应说明来源和许可；不能证明来源时先不合入。
4. 代码贡献按项目 MIT 许可接收，第三方内容保留原许可证与声明；这不是把第三方作品重新许可为 MIT。当前未建立 CLA/DCO 自动化，不宣称已签署或强制执行。
5. 问题关闭时注明修复提交/版本或不能处理的具体原因；重复项链接已有记录。跨 GitHub/Gitee 的同一问题应互相引用，避免两边给出矛盾结论。

### 问题分流与状态

数据丢失、已有数据被错误修改和安全问题优先评估，其次是可复现的执行或阅读阻断、兼容性问题，再处理功能建议与体验改进。优先级由影响范围、复现条件、可用替代方案和维护能力共同决定，不等同固定修复日期。敏感问题转入私密流程，公开记录不附利用细节。

| 状态 | 含义与应留下的记录 |
|---|---|
| 待复现 / 待补充 | 写明缺少的版本、步骤或最小数据；不能因为暂未复现就断言没有问题 |
| 已确认 | 记录复现环境、影响和判据；确认问题不等于已承诺排期 |
| 处理中 | 指向承担者和关联 PR/change；无人接手时不标为处理中 |
| 待验证 | 说明修复提交、验证方法与尚未覆盖项；不能把代码合入等同已发布修复 |
| 已关闭 | 注明已修复、重复、不采纳或信息不足等原因；修复项注明提交以及已发布版本或“待发布” |

暂缓项写明原因和重新评估条件。信息不足的记录在请求补充后仍无法判断时可以关闭，但应说明可凭新复现申请重开，不设置未实际配置的自动超时规则。跨平台重复项指定主记录并互相引用，结论保持一致。

### 审阅与响应

PR 就绪时需说明范围、行为变化、第三方来源、验证与限制。代码和构建配置变更按开发工作流完成门禁；纯文档修订核对事实、链接与格式。无法执行的检查明确记为未运行，由维护者补验或保持待验证，不以旧结果勾选通过。

审阅意见区分必须解决的问题与可选建议。更新代码后，重新核查受影响的行为与检查结果；最终接受、暂缓或拒绝均在原记录说明。非作者审阅可按需邀请；尚无常设独立团队，也不声称分支保护、必需审批或自动合入已启用。

普通 Issue/PR 不承诺固定响应时限，安全报告的首次回应目标仅适用于根安全策略。每次处理尽量留下状态、下一步和阻碍；不以自动回复或 AI 审阅冒充维护者已经受理。长期无法投入时在仓库说明维护放缓和受理范围，不继续承诺原排期。

### 最小处理记录

直接在 Issue/PR 中保留以下信息即可，无须建立第二套工单系统。首次人工回应与关闭时间可引用平台时间戳；没有实际事件时记为“未统计”，不填示例数字。

| 字段 | 记录内容 |
|---|---|
| 主记录与关联项 | 平台链接、跨平台重复项、PR 或 change |
| 影响与状态 | 版本/提交、类型、复现情况、当前状态及负责人（无人接手时写待分配） |
| 处理与验证 | 采用或拒绝的理由、修复提交、检查结果、未覆盖范围 |
| 收口与发布 | 关闭原因、修复所在版本或待发布状态、重新评估条件 |

私密报告、身份信息和未披露漏洞不进入公开统计明细；公开汇总只保留必要且不泄露个人信息的结论。

## 发布与兼容性

代码或构建配置变更按贡献指南运行 `pnpm check:ci`。发布记录还应包含目标平台、源码提交、锁文件、产物哈希、变更说明、已知限制及实际测试结果。环境导致某项检查不能执行时，必须说明替代检查和未覆盖部分。门禁通过、完成构建、实包验收和公开发布分别记录，不用其中一项代替其他项。

当前打包目标为 Windows x64。新增平台、破坏数据格式或更改旧轨迹读取行为时，应另行明确兼容策略与迁移验证。日常维护范围见[版本与维护政策](maintenance-policy.md)，安全报告受理范围以根安全策略为准，均不新增长期维护版本承诺。

第三方许可证检查应覆盖实际发行内容，包含被打进前端 bundle 的依赖以及 Electron/Chromium 附带声明。源代码使用 MIT 不代表所有依赖都是 MIT。参见 [依赖核查报告](audits/2026-09-27-dependency-licenses.md)。

新增或更新依赖时记录用途、锁定版本、上游来源、许可及所需声明；第三方代码与素材保留适用的版权和 NOTICE，不因复制进入仓库而改标 MIT。双许可证记录采用的许可路径；来源或分发条件无法确定时先解决该问题，再接受贡献或发布。元数据扫描只是核查输入，不作为全部依赖合规的结论。

发布由维护者确认，同一版本在 GitHub/Gitee 的提交、资产和哈希应可对应；某一端尚未同步时明确注明。发现发布缺陷时记录影响版本、可用规避办法和后续修复版本；避免静默替换同名资产造成哈希变化。涉及数据格式时先说明兼容范围与备份要求，不能假设旧包可读取新格式。

## 持续维护计划

以下是建议执行顺序和完成条件，不是已承诺日期。默认由当前维护者协调；任务确定后再在对应 Issue/change 中落实负责人和范围。

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| 当前文档阶段 | 明确职责、问题状态、贡献许可、审阅要求与安全报告流程 | 入口可导航，规则与实际运营状态分开 |
| 下一次发布准备 | 核实私密报告渠道；核对发行物第三方声明；记录构建与运行结果 | 有可验证渠道、有产物检查记录，问题在发布前处理 |
| 后续稳定迭代 | 优先处理数据完整性、错误诊断、兼容性和高频使用阻碍 | 每项可追溯至问题、实现和验证；依赖更新有回归依据 |
| 出现持续贡献者后 | 为明确模块引入第二维护者，逐步交接审阅和发布能力 | 有连续贡献记录、交接说明、实际完成的独立维护任务 |

单一维护者是当前持续性风险。缓解方式包括可重复构建、清晰的数据格式和错误语义、可运行的测试、发布步骤和最小权限交接；这些只能降低交接成本，不能替代实际的人力和时间投入。

建议每次发布记录未解决缺陷、Issue 首次响应与关闭时长、外部贡献与维护者投入。没有记录时标记“未统计”，不补造历史数字。维护投入长期不足时，应公开缩小维护范围或标记维护放缓，并更新支持策略，而不是继续承诺无法执行的路线图。

维护交接至少说明活动问题、支持版本、构建与发布步骤、数据兼容限制和各平台权限范围；密钥不写入交接文档或仓库。交接完成应有实际接收人和职责记录；当前尚无第二维护者，不把自动化工具当作人员接替。

- 验证安全报告入口并修正文案，由维护者实际接收一条测试报告后闭环。

- 核实远程标签、分支保护和审阅设置；配置存在前不能声称强制执行。
- 在有持续贡献基础后再确定维护者扩充与交接安排。
